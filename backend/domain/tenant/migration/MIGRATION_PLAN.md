## 🎯 迁移策略

采用**渐进式双写迁移方案**，分5个阶段执行：

```
┌─────────────────────────────────────────────────────────────┐
│  阶段1: DDL变更（Day 1）                                     │
│  - 添加 tenant_id VARCHAR(36) NULL 字段                     │
│  - 添加索引 idx_tenant_id                                    │
│  - 添加外键约束 ON DELETE CASCADE                           │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  阶段2: 数据迁移（Day 2-4）                                  │
│  - 分批处理，每批1000条                                     │
│  - 从 users 表查找 tenant_id                                │
│  - 批量更新 tenant_id                                       │
│  - 批次之间休息100ms，避免锁表                              │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  阶段3: 双写验证（Day 5-6）                                 │
│  - 启动双写模式（同时读写新旧字段）                         │
│  - 持续至少1周                                              │
│  - 数据一致性要求 ≥ 99.9%                                   │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  阶段4: 切换（Day 7）                                        │
│  - 修改 tenant_id 为 NOT NULL                               │
│  - 更新所有查询，使用 tenant_id                             │
│  - 移除双写逻辑                                             │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  阶段5: 清理（Day 8，保留1周后执行）                        │
│  - 删除旧字段（谨慎！建议保留1周观察期）                    │
│  - 删除旧索引                                               │
│  - 更新文档                                                 │
└─────────────────────────────────────────────────────────────┘
```

## 🔄 回滚方案

### 每个阶段的回滚策略

#### 阶段1回滚：删除字段
```sql

ALTER TABLE bots DROP COLUMN tenant_id;
ALTER TABLE bots DROP INDEX idx_tenant_id;
```

#### 阶段2回滚：清空已迁移数据
```sql
-- 如果数据迁移出现问题，清空tenant_id
```

#### 阶段3回滚：关闭双写模式

## ⚠️ 风险与应对

### 风险1: 大表迁移耗时过长
**表**: messages（~1000万条记录）
**风险**: 迁移可能需要数小时，影响业务
**应对**:
- 增大批次大小（2000条/批）
- 优化查询索引
- 选择业务低峰期执行（凌晨2:00-6:00）

### 风险2: 外键完整性问题
**风险**: 部分 user_id 在 users 表不存在
**应对**:
- 使用默认租户 `tenant_default`
- 记录异常日志，人工修复

### 风险3: 双写期间数据不一致
**风险**: 新旧字段数据不一致
**应对**:
- 实时监控一致性
- 不一致率 > 0.1% 立即告警
- 准备回滚方案

### 风险4: 切换后业务异常
**风险**: 某些查询未更新，导致数据错误
**应对**:
- 切换前完整的回归测试
- 准备快速回滚脚本
- 保留旧字段1周观察期
