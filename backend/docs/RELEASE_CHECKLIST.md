## 🚀 发布流程

### 阶段 1: 预发布检查（发布前 1 天）

1. **创建发布分支**: `git checkout -b release/org-v1.0.0`
2. **更新版本号**: 更新 `VERSION` 文件和代码中的版本号
3. **更新文档**: 更新所有相关文档
4. **代码审查**: 进行最终的代码审查
5. **创建 Release PR**: 提交 PR 到 `main` 分支

### 阶段 2: CI/CD 验证（发布前 2 小时）

1. **触发 CI 流水线**: 推送代码触发 CI
2. **验证 CI 检查**: 所有 CI 检查通过
3. **构建 Docker 镜像**: 镜像构建成功并推送
4. **安全扫描**: Trivy 扫描通过
5. **标记 Release**: 创建 Git tag `org-v1.0.0`

### 阶段 3: Staging 环境部署（发布前 1 小时）

1. **部署到 Staging**: 触发 CD 流水线
2. **烟雾测试**: 运行核心功能测试
3. **性能测试**: 运行性能测试
4. **集成测试**: 运行完整的集成测试
5. **验收测试**: 产品经理验收

### 阶段 4: Production 环境部署

#### 4.1 准备阶段（T-15 分钟）
1. **发送发布通知**: 提前通知相关人员
2. **检查监控**: 确认监控大盘正常
3. **准备回滚**: 确认回滚脚本可用

#### 4.2 执行灰度发布（T+0 分钟）
1. **10% 流量**: 发布到 10% 用户
   - 监控错误率、延迟
   - 观察 10 分钟
2. **50% 流量**: 扩大到 50% 用户
   - 继续监控
   - 观察 10 分钟
3. **100% 流量**: 全量发布
   - 持续监控

#### 4.3 验证阶段（T+30 分钟）
1. **健康检查**: 所有实例健康
2. **功能验证**: 核心功能正常
3. **性能验证**: 性能指标正常
4. **日志检查**: 无异常日志

#### 4.4 完成阶段（T+60 分钟）
1. **确认发布成功**: 所有指标正常
2. **发布通知**: 发送成功通知
3. **更新文档**: 更新发布记录
4. **归档**: 归档发布相关文档

## 🔄 回滚流程

### 触发条件
- 错误率 > 5% 持续 5 分钟
- P99 延迟 > 3s 持续 5 分钟
- 健康检查失败 > 50% 实例
- 数据不一致或数据丢失
- 发现严重安全漏洞

### 回滚步骤
1. **停止灰度**: 立即停止灰度发布
2. **执行回滚**:
   ```bash
   kubectl rollout undo deployment/org-center-api -n org-center-prod
   ```
3. **验证回滚**:
   ```bash
   kubectl rollout status deployment/org-center-api -n org-center-prod
   curl -f http://org-center-api/health
   ```
4. **数据库回滚**: 如需要，执行数据库回滚脚本
5. **回滚通知**: 发送回滚通知到所有相关人员

### 回滚后处理
1. **问题分析**: 分析失败原因
2. **修复问题**: 修复发现的问题
3. **重新测试**: 在 Staging 环境验证修复
4. **计划重新发布**: 制定重新发布计划
