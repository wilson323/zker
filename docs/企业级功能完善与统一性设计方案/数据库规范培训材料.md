### 2.2 知识点讲解

#### 2.2.1 范式化理论

**第一范式 (1NF): 字段原子性**

```sql
-- ❌ 违反1NF
CREATE TABLE users_bad (
    id BIGINT PRIMARY KEY,
    name VARCHAR(255),
    emails VARCHAR(1000)  -- 多个邮箱用逗号分隔
);

-- ✅ 符合1NF
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name VARCHAR(255)
);

CREATE TABLE user_emails (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    email VARCHAR(255) NOT NULL,
    FOREIGN KEY (user_id) REFERENCES users(id)
);
```

**练习1**: 识别以下表设计是否符合1NF
```sql
CREATE TABLE bots (
    id BIGINT PRIMARY KEY,
    name VARCHAR(255),
    tags VARCHAR(500)  -- 标签用逗号分隔
);
```

**答案**: ❌ 不符合1NF,`tags`字段应拆分为单独的表。

**第二范式 (2NF): 消除部分依赖**

```sql
-- ❌ 违反2NF
CREATE TABLE order_items_bad (
    order_id BIGINT,
    product_id BIGINT,
    product_name VARCHAR(255),  -- 依赖于product_id
    quantity INT,
    PRIMARY KEY (order_id, product_id)
);

-- ✅ 符合2NF
CREATE TABLE products (
    id BIGINT PRIMARY KEY,
    name VARCHAR(255)
);

CREATE TABLE order_items (
    id BIGINT PRIMARY KEY,
    order_id BIGINT,
    product_id BIGINT,
    quantity INT,
    price DECIMAL(10,2),  -- 快照价格
    FOREIGN KEY (product_id) REFERENCES products(id)
);
```

**第三范式 (3NF): 消除传递依赖**

```sql
-- ❌ 违反3NF
CREATE TABLE users_bad (
    id BIGINT PRIMARY KEY,
    name VARCHAR(255),
    city_id BIGINT,
    city_name VARCHAR(100),  -- 传递依赖
    province_name VARCHAR(100)
);

-- ✅ 符合3NF
CREATE TABLE cities (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100),
    province_id BIGINT
);

CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name VARCHAR(255),
    city_id BIGINT,
    FOREIGN KEY (city_id) REFERENCES cities(id)
);
```

#### 2.2.2 命名规范

**✅ 正确的命名**
```sql
CREATE TABLE bot_conversations (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    tenant_id VARCHAR(64) NOT NULL,
    bot_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    message_count INT DEFAULT 0,
    is_active BOOLEAN DEFAULT TRUE,

    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='Bot对话表';
```

**❌ 错误的命名**
```sql
CREATE TABLE botConversations (  -- ❌ 驼峰命名
    ID BIGINT PRIMARY KEY,         -- ❌ 应使用小写id
    TenantID VARCHAR(64),          -- ❌ 应使用下划线
    BotID BIGINT,
    UserID BIGINT,
    msgCount INT,                 -- ❌ 应使用完整单词
    active BOOLEAN,                -- ❌ 应使用is_前缀
    createTime DATETIME            -- ❌ 应使用created_at
);
```

**练习2**: 找出以下命名中的错误
```sql
CREATE TABLE UserBots (
    ID BIGINT PRIMARY KEY,
    BotName VARCHAR(255),
    status VARCHAR(50),
    CreateTime DATETIME
);
```

**答案**:
- ❌ 表名应使用`user_bots`(小写+下划线)
- ❌ 主键应使用`id`(小写)
- ❌ 字段应使用`bot_name`, `created_at`(下划线+小写)
- ❌ status应使用`ENUM`类型

#### 2.2.3 数据类型选择

**整型选择**
```sql
-- 主键/外键: BIGINT
id BIGINT PRIMARY KEY AUTO_INCREMENT
user_id BIGINT NOT NULL

-- 状态枚举: TINYINT
status TINYINT NOT NULL  -- 0-255

-- 计数: INT UNSIGNED
message_count INT UNSIGNED NOT NULL  -- 0-42亿
```

**字符串选择**
```sql
-- 短字符串: VARCHAR(长度)
name VARCHAR(255)
email VARCHAR(255)

-- 长文本: TEXT
description TEXT
content LONGTEXT

-- JSON数据: JSON
metadata JSON
settings JSON
```

**时间类型**
```sql
-- 业务时间: DATETIME
created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP

-- 日志时间: TIMESTAMP(支持时区)
logged_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
```

**小数类型**
```sql
-- 金额: DECIMAL(精度优先)
price DECIMAL(10, 2)  -- 总共10位,小数2位
amount DECIMAL(12, 4)

-- 评分: DECIMAL
rating DECIMAL(3, 2)  -- 如4.50分
```

## 3. 模块2: 索引优化实践

### 3.1 学习目标

- [ ] 理解索引原理
- [ ] 掌握索引设计原则
- [ ] 了解复合索引设计
- [ ] 学会使用EXPLAIN分析查询
- [ ] 避免索引失效的常见错误

### 3.2 知识点讲解

#### 3.2.1 索引原理

**B+树索引结构**:
```
           [Root]
           /    \
        [Internal]  [Internal]
        /  |  \    /  |  \
     [Leaf] [Leaf] ... [Leaf]
      |      |           |
    Data   Data        Data
```

**索引优势**:
- ✅ 快速查找: O(log n) vs O(n)全表扫描
- ✅ 有序存储: 支持范围查询和排序
- ✅ 覆盖索引: 无需回表,直接从索引获取数据

**索引劣势**:
- ❌ 占用存储空间
- ❌ 降低写入性能(需要更新索引)
- ❌ 维护成本(索引碎片)

#### 3.2.2 索引设计原则

**1. 选择合适的索引列**

```sql
-- ✅ 适合建索引的列
WHERE user_id = 123          -- 高选择性
ORDER BY created_at DESC      -- 排序字段
JOIN bots ON b.id = ...       -- 关联字段

-- ❌ 不适合建索引的列
WHERE gender = 'male'         -- 低选择性(只有2-3个值)
WHERE status = 'active'       -- 大部分数据都是active
```

**2. 复合索引设计(最左前缀原则)**

```sql
-- 创建复合索引
CREATE INDEX idx_user_status_created
ON bot_conversations(user_id, status, created_at DESC);

-- ✅ 可以使用索引的查询
WHERE user_id = 123;
WHERE user_id = 123 AND status = 'active';
WHERE user_id = 123 AND status = 'active' ORDER BY created_at DESC;

-- ❌ 无法使用索引的查询
WHERE status = 'active';                    -- 跳过了user_id
WHERE created_at > '2025-01-01';            -- 跳过了user_id和status
```

**练习4**: 分析以下复合索引的使用情况

```sql
CREATE INDEX idx_bot_status_created
ON bot_conversations(bot_id, status, created_at DESC);

-- 查询1: WHERE bot_id = 123 AND status = 'active'
-- 查询2: WHERE bot_id = 123 ORDER BY created_at DESC
-- 查询3: WHERE status = 'active'
-- 查询4: WHERE created_at > '2025-01-01'
```

**答案**:
- 查询1: ✅ 使用索引(使用bot_id和status列)
- 查询2: ✅ 使用索引(使用bot_id列)
- 查询3: ❌ 不使用索引(跳过了bot_id)
- 查询4: ❌ 不使用索引(跳过了bot_id和status)

#### 3.2.3 使用EXPLAIN分析查询

```sql
EXPLAIN SELECT * FROM bot_conversations
WHERE user_id = 123 AND status = 'active'
ORDER BY created_at DESC LIMIT 20;

-- 关键指标:
-- type: 查询类型
--   - ALL: 全表扫描(最差)
--   - index: 索引扫描
--   - range: 范围扫描
--   - ref: 索引查找(较好)
--   - const: 主键或唯一索引查找(最好)
--
-- rows: 预估扫描行数(越少越好)
--
-- Extra: 额外信息
--   - Using index: 使用覆盖索引(无需回表)
--   - Using filesort: 需要文件排序(不好)
--   - Using temporary: 使用临时表(不好)
```

**练习5**: 分析以下查询的执行计划

```sql
EXPLAIN SELECT * FROM bot_messages
WHERE conversation_id = 123
ORDER BY created_at DESC
LIMIT 20;
```

**预期结果**:
- type: ref (使用索引查找conversation_id)
- rows: 较少(假设该对话有100条消息)
- Extra: Using filesort(如果created_at无索引)

**优化建议**:
```sql
-- 创建复合索引
CREATE INDEX idx_conversation_created
ON bot_messages(conversation_id, created_at DESC);
```

#### 3.2.4 避免索引失效

**常见错误**:
```sql
-- 1. 在索引列上使用函数
-- ❌ WHERE DATE(created_at) = '2025-01-30'
-- ✅ WHERE created_at >= '2025-01-30' AND created_at < '2025-01-31'

-- 2. 隐式类型转换
-- ❌ WHERE phone = 13800138000  (phone是VARCHAR)
-- ✅ WHERE phone = '13800138000'

-- 3. 前缀模糊查询
-- ❌ WHERE name LIKE '%张%'
-- ✅ WHERE name LIKE '张%'

-- 4. OR连接(如果没有索引)
-- ❌ WHERE user_id = 123 OR status = 1
-- ✅ WHERE user_id = 123 UNION ALL WHERE status = 1

-- 5. 负向查询
-- ❌ WHERE status != 1
-- ✅ WHERE status IN (1, 2, 3)
```

### 3.3 实战练习

**练习6**: 优化慢查询

**慢查询SQL**:
```sql
SELECT * FROM bot_messages
WHERE user_id = 123
  AND DATE(created_at) = '2025-01-30'
ORDER BY created_at DESC
LIMIT 20;
```

**优化步骤**:
1. 使用EXPLAIN分析
2. 识别问题: 函数破坏索引 + 无索引
3. 优化SQL
4. 添加索引
5. 验证优化效果

**优化后SQL**:
```sql
-- 优化1: 去除函数
SELECT * FROM bot_messages
WHERE user_id = 123
  AND created_at >= '2025-01-30'
  AND created_at < '2025-01-31'
ORDER BY created_at DESC
LIMIT 20;

-- 优化2: 创建索引
CREATE INDEX idx_user_created
ON bot_messages(user_id, created_at DESC);

-- 优化3: 覆盖索引(如果只查询特定字段)
SELECT id, user_id, content, created_at
FROM bot_messages
WHERE user_id = 123
  AND created_at >= '2025-01-30'
  AND created_at < '2025-01-31'
ORDER BY created_at DESC
LIMIT 20;

-- 覆盖索引
CREATE INDEX idx_user_created_cover
ON bot_messages(user_id, created_at DESC, id, content);
```

### 4.2 知识点讲解

#### 4.2.1 SQL优化技巧

**技巧1: 避免SELECT ***
```sql
-- ❌ 查询所有列
SELECT * FROM bots WHERE id = 123;

-- ✅ 只查询需要的列
SELECT id, name, status FROM bots WHERE id = 123;
```

**技巧2: 优化JOIN**
```sql
-- ❌ 交叉连接(笛卡尔积)
SELECT * FROM bots, plugins;

-- ✅ 使用INNER JOIN
SELECT b.*, p.*
FROM bots b
INNER JOIN bot_plugins bp ON b.id = bp.bot_id
INNER JOIN plugins p ON bp.plugin_id = p.id;
```

**技巧3: 优化子查询**
```sql
-- ❌ 子查询
SELECT * FROM bots
WHERE id IN (SELECT bot_id FROM bot_conversations WHERE user_id = 123);

-- ✅ 改用JOIN
SELECT DISTINCT b.*
FROM bots b
INNER JOIN bot_conversations c ON b.id = c.bot_id
WHERE c.user_id = 123;
```

**技巧4: 分页优化**
```sql
-- ❌ 深分页(性能差)
SELECT * FROM bot_messages
ORDER BY id
LIMIT 1000000, 20;

-- ✅ 使用游标分页
-- 首次查询
SELECT * FROM bot_messages
ORDER BY id
LIMIT 20;

-- 后续查询(记住上一页最后的id)
SELECT * FROM bot_messages
WHERE id > 上一页最后的id
ORDER BY id
LIMIT 20;

-- ✅ 使用延迟关联
SELECT * FROM bot_messages
WHERE id > (
  SELECT id FROM bot_messages
  ORDER BY id
  LIMIT 1000000, 1
)
ORDER BY id
LIMIT 20;
```

#### 4.2.3 缓存策略

**Redis缓存**
```python
# 缓存Bot信息
cache_key = f"bot:{bot_id}"
bot = redis.get(cache_key)

if not bot:
    # 缓存未命中,查询数据库
    bot = db.query("SELECT * FROM bots WHERE id = ?", bot_id)
    # 写入缓存(TTL=1小时)
    redis.setex(cache_key, 3600, json.dumps(bot))

return bot
```

**查询结果缓存**
```python
# 缓存热点查询结果
def get_bot_list(tenant_id, status):
    cache_key = f"bot_list:{tenant_id}:{status}"
    cached = redis.get(cache_key)

    if cached:
        return json.loads(cached)

    bots = db.query("""
        SELECT * FROM bots
        WHERE tenant_id = ? AND status = ?
        ORDER BY created_at DESC
        LIMIT 20
    """, tenant_id, status)

    redis.setex(cache_key, 600, json.dumps(bots))  # 缓存10分钟
    return bots

# 更新时失效缓存
def update_bot(bot_id, data):
    db.update("bots", data, id=bot_id)
    # 失效相关缓存
    redis.delete(f"bot:{bot_id}")
    redis.delete(f"bot_list:{tenant_id}:*")
```

### 5.2 知识点讲解

#### 5.2.1 迁移流程

**标准流程**:
```
1. 评估(数据量、表结构、依赖关系)
2. 备份(全库备份 + 增量备份)
3. 测试(在测试环境验证)
4. 执行(选择业务低峰期)
5. 验证(数据完整性、业务功能)
6. 监控(性能、错误日志)
7. 清理(删除旧数据/备份)
```

#### 5.2.2 迁移脚本示例

#### 5.2.3 数据验证方法

**方法1: 行数对比**
```sql
-- 对比主表和归档表的数据行数
SELECT '主表' AS source, COUNT(*) AS count FROM bot_messages
UNION ALL
SELECT '归档表' AS source, COUNT(*) AS count FROM bot_messages_archive;
```

### 6.2 案例2: 高并发写入优化

**场景**: Bot消息写入频繁(每秒1000次写入),出现锁等待

**问题**:
```sql
-- 频繁出现锁等待
SELECT * FROM information_schema.innodb_lock_waits;

-- 统计信息
SHOW ENGINE INNODB STATUS\G

-- 结果: 大量行锁,事务等待时间过长
```

**分析**:
```sql
-- 问题SQL
UPDATE bot_conversations
SET message_count = message_count + 1
WHERE id = 12345;

-- 问题: 每次消息插入都更新conversation,导致行锁竞争
```

**优化方案**:

**方案1: 批量更新**
```python
# 收积批量更新
pending_updates = {}

def on_message_insert(conversation_id, message_id):
    # 计数+1
    pending_updates[conversation_id] = pending_updates.get(conversation_id, 0) + 1

    # 每秒批量更新一次
    if len(pending_updates) > 100:
        batch_update()

def batch_update():
    for conversation_id, count in pending_updates.items():
        db.execute(
            "UPDATE bot_conversations SET message_count = message_count + ? WHERE id = ?",
            (count, conversation_id)
        )
    pending_updates.clear()
```

**方案2: 异步更新**
```python
# 使用消息队列异步更新
def on_message_insert(conversation_id, message_id):
    # 发送到消息队列
    queue.publish('update_message_count', {'conversation_id': conversation_id})

# 后台worker处理
def worker():
    for message in queue.consume('update_message_count'):
        db.execute(
            "UPDATE bot_conversations SET message_count = message_count + 1 WHERE id = ?",
            (1, message['conversation_id'])
        )
```

## 10. 常见问题FAQ

### Q1: 什么时候应该建索引?
**A**:
- ✅ WHERE条件字段
- ✅ ORDER BY字段(高频查询)
- ✅ JOIN关联字段
- ✅ 外键字段
- ❌ 低选择性字段(如gender)
- ❌ 频繁更新的字段

### Q2: 如何判断索引是否有效?
**A**:
```sql
-- 1. 查看索引使用情况
SELECT * FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE object_name = 'bots';

-- 2. 分析查询执行计划
EXPLAIN SELECT ...;

-- 3. 查看慢查询日志
SELECT * FROM mysql.slow_log
WHERE sql_text LIKE '%bots%';
```

### Q3: 什么时候需要分表?
**A**:
- 单表数据量>2000万
- 单表数据文件>10GB
- 查询响应时间>500ms
- 无法通过索引优化

### Q4: 如何进行数据库迁移?
**A**:
1. 评估数据量和表结构
2. 备份数据库
3. 在测试环境验证
4. 编写迁移脚本
5. 选择业务低峰期执行
6. 验证数据完整性
7. 监控性能和错误日志

### Q5: 如何优化慢查询?
**A**:
1. 使用EXPLAIN分析执行计划
2. 避免SELECT *
3. 优化WHERE条件(使用索引)
4. 优化JOIN(小表驱动大表)
5. 优化子查询(改为JOIN)
6. 添加合适的索引
7. 考虑使用缓存
