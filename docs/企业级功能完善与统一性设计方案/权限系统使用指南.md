# 权限系统使用指南

## 概述

ZKER 企业级权限系统基于 RBAC（Role-Based Access Control）模型，提供了**5级数据权限**和**3级字段权限**，支持复杂的权限控制需求。

## 核心概念

### 1. 用户角色

用户通过角色（Role）获得权限，一个用户可以拥有多个角色。

### 2. 数据权限范围

- **ALL**: 全部数据权限
- **DEPARTMENT**: 部门及子部门数据权限
- **OWN**: 仅自己创建的数据
- **CUSTOM**: 自定义过滤条件
- **NONE**: 无权限

### 3. 字段权限级别

- **editable**: 可编辑
- **readonly**: 只读
- **hidden**: 隐藏

## API 使用指南

### 1. 角色管理

#### 1.1 创建角色

**接口**: `POST /roles`

**请求参数**:
```json
{
  "tenant_id": "tenant_abc123",
  "role_code": "sales_manager",
  "role_name": "销售经理",
  "role_type": "custom",
  "description": "销售部门经理角色",
  "parent_role_id": null
}
```

**响应示例**:
```json
{
  "code": 0,
  "message": "success",
  "data": {
    "role_id": "role_xyz789",
    "role_code": "sales_manager",
    "role_name": "销售经理",
    "role_type": "custom",
    "created_at": 1704067200000
  }
}
```

#### 1.2 为用户分配角色

**接口**: `POST /users/{user_id}/roles`

**请求参数**:
```json
{
  "tenant_id": "tenant_abc123",
  "role_id": "role_xyz789"
}
```

**响应示例**:
```json
{
  "code": 0,
  "message": "success",
  "data": {
    "user_id": "user_123",
    "role_id": "role_xyz789",
    "assigned_at": 1704067200000
  }
}
```

#### 1.3 获取用户的所有角色

**接口**: `GET /users/{user_id}/roles`

**响应示例**:
```json
{
  "code": 0,
  "message": "success",
  "data": {
    "roles": [
      {
        "role_id": "role_xyz789",
        "role_code": "sales_manager",
        "role_name": "销售经理",
        "permissions": {
          "bots": "ALL",
          "workflows": "DEPARTMENT"
        }
      }
    ]
  }
}
```

### 2. 数据权限配置

#### 2.1 设置角色数据权限

**接口**: `POST /roles/{role_id}/data-permissions`

**请求参数**:
```json
{
  "tenant_id": "tenant_abc123",
  "resource_type": "bots",
  "scope": "DEPARTMENT",
  "department_id": "dept_123",
  "custom_filter": null
}
```

**scope 参数说明**:
- `ALL`: 无需其他参数
- `DEPARTMENT`: 需要提供 `department_id`，部门领导可访问子部门
- `OWN`: 无需其他参数
- `CUSTOM`: 需要提供 `custom_filter`（JSON格式的过滤条件）
- `NONE`: 无权限

**custom_filter 示例**:
```json
{
  "conditions": [
    {"field": "status", "operator": "eq", "value": "active"},
    {"field": "priority", "operator": "gte", "value": 5}
  ],
  "logic": "AND"
}
```

#### 2.2 检查数据权限

**接口**: `POST /permissions/check-data`

**请求参数**:
```json
{
  "user_id": "user_123",
  "tenant_id": "tenant_abc123",
  "resource_type": "bots",
  "resource_id": "bot_456"
}
```

**响应示例**（有权限）:
```json
{
  "code": 0,
  "message": "success",
  "data": {
    "allowed": true,
    "scope": "DEPARTMENT",
    "reasons": ["用户属于销售部门，可访问部门及子部门数据"]
  }
}
```

**响应示例**（无权限）:
```json
{
  "code": "PERMISSION_DENIED",
  "message": "权限不足",
  "details": {
    "user_id": "user_123",
    "resource_type": "bots",
    "resource_id": "bot_456",
    "required_scope": "DEPARTMENT",
    "actual_scope": "OWN"
  }
}
```

### 3. 字段权限配置

#### 3.1 设置角色字段权限

**接口**: `POST /roles/{role_id}/field-permissions`

**请求参数**:
```json
{
  "tenant_id": "tenant_abc123",
  "resource_type": "bots",
  "permissions": [
    {
      "field_name": "name",
      "permission_level": "readonly"
    },
    {
      "field_name": "config",
      "permission_level": "hidden"
    },
    {
      "field_name": "status",
      "permission_level": "editable"
    }
  ]
}
```

#### 3.2 获取字段权限

**接口**: `GET /users/{user_id}/field-permissions`

**查询参数**:
- `resource_type`: 资源类型（必填）

**响应示例**:
```json
{
  "code": 0,
  "message": "success",
  "data": {
    "permissions": {
      "name": "readonly",
      "config": "hidden",
      "status": "editable",
      "created_at": "editable"
    }
  }
}
```

### 4. 部门权限

#### 4.1 创建部门

**接口**: `POST /departments`

**请求参数**:
```json
{
  "tenant_id": "tenant_abc123",
  "department_name": "销售部",
  "parent_department_id": null
}
```

**响应示例**:
```json
{
  "code": 0,
  "message": "success",
  "data": {
    "department_id": "dept_123",
    "department_name": "销售部",
    "tenant_id": "tenant_abc123",
    "created_at": 1704067200000
  }
}
```

#### 4.2 添加用户到部门

**接口**: `POST /departments/{department_id}/members`

**请求参数**:
```json
{
  "user_id": "user_123",
  "tenant_id": "tenant_abc123",
  "is_leader": false
}
```

#### 4.3 设置部门领导

**接口**: `PUT /departments/{department_id}/members/{user_id}`

**请求参数**:
```json
{
  "is_leader": true
}
```

**说明**: 部门领导可以访问该部门及其所有子部门的数据。

#### 4.4 获取用户可访问的部门

**接口**: `GET /users/{user_id}/accessible-departments`

**响应示例**:
```json
{
  "code": 0,
  "message": "success",
  "data": {
    "accessible_department_ids": ["dept_123", "dept_124", "dept_125"],
    "departments": [
      {
        "department_id": "dept_123",
        "department_name": "销售部",
        "is_leader": true,
        "has_children": true
      }
    ]
  }
}
```

## 使用场景示例

### 场景1: 销售经理权限配置

**需求**: 销售经理可以查看和编辑整个销售部门的Bot，但不能修改其他部门的Bot。

**实现步骤**:

1. 创建"销售经理"角色
2. 设置数据权限为 `DEPARTMENT`，指定销售部门ID
3. 设置字段权限：
   - `name`: readonly
   - `config`: editable
   - `api_key`: hidden

```bash
# 1. 创建角色
curl -X POST https://api.zker.com/v1/roles \
  -H "Authorization: Bearer TOKEN" \
  -d '{
    "tenant_id": "tenant_abc123",
    "role_code": "sales_manager",
    "role_name": "销售经理"
  }'

# 2. 设置数据权限
curl -X POST https://api.zker.com/v1/roles/role_xyz789/data-permissions \
  -H "Authorization: Bearer TOKEN" \
  -d '{
    "tenant_id": "tenant_abc123",
    "resource_type": "bots",
    "scope": "DEPARTMENT",
    "department_id": "dept_sales"
  }'

# 3. 设置字段权限
curl -X POST https://api.zker.com/v1/roles/role_xyz789/field-permissions \
  -H "Authorization: Bearer TOKEN" \
  -d '{
    "tenant_id": "tenant_abc123",
    "resource_type": "bots",
    "permissions": [
      {"field_name": "name", "permission_level": "readonly"},
      {"field_name": "config", "permission_level": "editable"},
      {"field_name": "api_key", "permission_level": "hidden"}
    ]
  }'
```

### 场景2: 自定义过滤条件

**需求**: 用户只能访问状态为"active"且优先级大于等于5的Bot。

**实现步骤**:

1. 设置数据权限为 `CUSTOM`
2. 提供自定义过滤条件

```bash
curl -X POST https://api.zker.com/v1/roles/role_xyz789/data-permissions \
  -H "Authorization: Bearer TOKEN" \
  -d '{
    "tenant_id": "tenant_abc123",
    "resource_type": "bots",
    "scope": "CUSTOM",
    "custom_filter": "[{\"field\":\"status\",\"operator\":\"eq\",\"value\":\"active\"},{\"field\":\"priority\",\"operator\":\"gte\",\"value\":5,\"logic\":\"AND\"}]"
  }'
```

### 场景3: 多角色权限聚合

**需求**: 用户同时拥有"销售经理"和"技术顾问"两个角色，需要合并权限。

**权限聚合规则**:
- **数据权限**: 取权限最大的（ALL > DEPARTMENT > OWN > CUSTOM > NONE）
- **字段权限**: 取权限最大的（editable > readonly > hidden）

**实现**:

```bash
# 分配第一个角色
curl -X POST https://api.zker.com/v1/users/user_123/roles \
  -H "Authorization: Bearer TOKEN" \
  -d '{
    "tenant_id": "tenant_abc123",
    "role_id": "role_sales_manager"
  }'

# 分配第二个角色
curl -X POST https://api.zker.com/v1/users/user_123/roles \
  -H "Authorization: Bearer TOKEN" \
  -d '{
    "tenant_id": "tenant_abc123",
    "role_id": "role_tech_advisor"
  }'
```

## 自定义过滤条件语法

### 支持的操作符

| 操作符 | 说明 | 示例 |
|--------|------|------|
| `eq` | 等于 | `{"field": "status", "operator": "eq", "value": "active"}` |
| `ne` | 不等于 | `{"field": "type", "operator": "ne", "value": "deprecated"}` |
| `gt` | 大于 | `{"field": "priority", "operator": "gt", "value": 5}` |
| `lt` | 小于 | `{"field": "count", "operator": "lt", "value": 100}` |
| `gte` | 大于等于 | `{"field": "priority", "operator": "gte", "value": 5}` |
| `lte` | 小于等于 | `{"field": "count", "operator": "lte", "value": 100}` |
| `in` | 在列表中 | `{"field": "type", "operator": "in", "value": ["bot", "workflow"]}` |
| `not_in` | 不在列表中 | `{"field": "status", "operator": "not_in", "value": ["deleted", "archived"]}` |
| `contains` | 包含字符串 | `{"field": "name", "operator": "contains", "value": "test"}` |
| `starts_with` | 以...开头 | `{"field": "name", "operator": "starts_with", "value": "bot_"}` |
| `ends_with` | 以...结尾 | `{"field": "email", "operator": "ends_with", "value": "@example.com"}` |
| `is_null` | 为null | `{"field": "deleted_at", "operator": "is_null"}` |
| `is_not_null` | 不为null | `{"field": "created_at", "operator": "is_not_null"}` |

### 逻辑组合

默认使用 **AND** 逻辑，可以通过 `logic` 字段改为 **OR**。

**AND 示例**（必须同时满足所有条件）:
```json
[
  {"field": "status", "operator": "eq", "value": "active"},
  {"field": "priority", "operator": "gte", "value": 5}
]
```

**OR 示例**（满足任一条件即可）:
```json
[
  {"field": "status", "operator": "eq", "value": "active"},
  {"field": "status", "operator": "eq", "value": "pending", "logic": "OR"}
]
```

**混合逻辑**:
```json
[
  {"field": "type", "operator": "eq", "value": "bot"},
  {"field": "priority", "operator": "gte", "value": 8},
  {"field": "status", "operator": "eq", "value": "active", "logic": "OR"}
]
```
等价于: `(type == 'bot' AND priority >= 8) OR (status == 'active')`

## 错误码列表

| 错误码 | 说明 | HTTP状态码 |
|--------|------|-----------|
| `PERMISSION_DENIED` | 权限不足 | 403 |
| `ROLE_NOT_FOUND` | 角色不存在 | 404 |
| `ROLE_ALREADY_EXISTS` | 角色已存在 | 409 |
| `DEPARTMENT_NOT_FOUND` | 部门不存在 | 404 |
| `USER_NOT_IN_DEPARTMENT` | 用户不在部门中 | 400 |
| `INVALID_FILTER_CONDITION` | 无效的过滤条件 | 400 |

## 最佳实践

### 1. 角色设计

- ✅ 按照职责划分角色（如：销售经理、技术顾问、普通用户）
- ✅ 使用清晰的命名规范（如：`sales_manager`, `tech_advisor`）
- ❌ 避免创建过多角色（建议 < 20个/租户）
- ❌ 避免角色职责重叠

### 2. 权限分配

- ✅ 遵循最小权限原则
- ✅ 定期审查用户权限
- ❌ 避免直接分配给个人（应通过角色）
- ❌ 避免过度使用ALL权限

### 3. 性能优化

- ✅ 使用缓存存储用户权限信息
- ✅ 批量查询权限而非逐个查询
- ✅ 在业务层缓存权限检查结果

### 4. 部门设计

- ✅ 保持部门层级扁平（建议 < 5层）
- ✅ 定期清理空部门
- ✅ 使用部门领导权限谨慎
