## 🎯 性能基线概述

### 基线定义

**性能基线** 是系统在正常负载下应达到的性能指标标准，包括：

1. **响应时间基线**：API、数据库、缓存的响应时间
2. **吞吐量基线**：系统每秒可处理的请求数
3. **并发能力基线**：系统可支持的最大并发用户数
4. **资源使用基线**：CPU、内存、磁盘的使用率
5. **错误率基线**：系统允许的错误率范围

### 性能等级

| 等级 | 说明 | 适用场景 |
|------|------|---------|
| **正常** | 所有指标在基线范围内 | 日常运营 |
| **警告** | 部分指标超出基线，但系统可用 | 流量高峰 |
| **严重** | 多个指标超出基线，系统降级 | 故障状态 |
| **危急** | 系统不可用或即将崩溃 | 紧急故障 |

## 💻 系统资源基线

### CPU 使用率

| 场景 | 基线 | 说明 |
|------|------|------|
| **正常负载** | < 60% | 100 并发用户 |
| **高负载** | 60% - 80% | 200 并发用户 |
| **警告阈值** | > 80% | 持续5分钟 |
| **严重阈值** | > 90% | 持续2分钟 |

**优化建议**:
- CPU 使用率 > 80%：考虑扩容或优化算法
- CPU 使用率 > 90%：立即扩容或限流

### 内存使用率

| 场景 | 基线 | 说明 |
|------|------|------|
| **正常负载** | < 70% | 100 并发用户 |
| **高负载** | 70% - 85% | 200 并发用户 |
| **警告阈值** | > 85% | 持续5分钟 |
| **严重阈值** | > 95% | 持续2分钟 |

**优化建议**:
- 内存使用率 > 85%：检查内存泄漏，优化缓存
- 内存使用率 > 95%：立即扩容或重启服务

### 磁盘使用率

| 场景 | 基线 | 说明 |
|------|------|------|
| **正常** | < 80% | 日常运营 |
| **警告阈值** | > 85% | 需要清理日志 |
| **严重阈值** | > 95% | 立即扩容或清理 |

**优化建议**:
- 定期清理日志和临时文件
- 使用日志轮转（logrotate）
- 监控磁盘增长趋势

### 网络带宽

| 指标 | 基线 | 说明 |
|------|------|------|
| **入站带宽** | < 70% 峰值 | 1 Gbps 网络 |
| **出站带宽** | < 70% 峰值 | 1 Gbps 网络 |
| **网络延迟** | < 1ms (同机房) | 数据库连接 |

## 🌐 API 性能基线

### API 响应时间

| API 类型 | P50 (中位数) | P95 | P99 | 说明 |
|---------|------------|-----|-----|------|
| **健康检查** | < 10ms | < 20ms | < 50ms | /health, /ready |
| **租户列表** | < 100ms | < 300ms | < 500ms | GET /api/tenants |
| **租户详情** | < 50ms | < 200ms | < 300ms | GET /api/tenants/:id |
| **配额查询** | < 100ms | < 500ms | < 1000ms | GET /api/tenants/:id/quotas |
| **配额检查** | < 50ms | < 500ms | < 1000ms | POST /api/tenants/:id/quotas/check |
| **Bot 列表** | < 200ms | < 1000ms | < 2000ms | GET /api/bots (分页) |
| **Bot 创建** | < 500ms | < 2000ms | < 3000ms | POST /api/bots |
| **权限检查** | < 10ms | < 200ms | < 500ms | POST /api/permissions/check-data |
| **角色列表** | < 100ms | < 500ms | < 1000ms | GET /api/roles |
| **权限矩阵** | < 500ms | < 2000ms | < 5000ms | GET /api/permissions/matrix |

**说明**:
- **P50**：50% 的请求响应时间
- **P95**：95% 的请求响应时间（SLA 指标）
- **P99**：99% 的请求响应时间

### API 吞吐量

| API 类型 | 基线 (RPS) | 峰值 (RPS) | 说明 |
|---------|------------|-----------|------|
| **GET 请求** | > 100 | > 500 | 只读操作 |
| **POST 请求** | > 50 | > 200 | 写入操作 |
| **权限检查** | > 500 | > 1000 | 高频操作 |
| **配额检查** | > 200 | > 500 | 中频操作 |

### API 错误率

| 级别 | 基线 | 说明 |
|------|------|------|
| **正常** | < 0.1% | 100 并发用户 |
| **警告** | 0.1% - 1% | 需要关注 |
| **严重** | 1% - 5% | 需要立即处理 |
| **危急** | > 5% | 系统不可用 |

### 连接池配置

| 参数 | 基线值 | 说明 |
|------|--------|------|
| **最大连接数** | 200 | MySQL max_connections |
| **活跃连接数** | < 80% | 警告阈值 |
| **空闲连接数** | > 10% | 最小空闲连接 |
| **连接超时** | 5秒 | 连接建立超时 |

### 查询性能

| 查询类型 | P95 基线 | P99 基线 | 说明 |
|---------|---------|---------|------|
| **简单查询** (单表) | < 10ms | < 50ms | WHERE 主键查询 |
| **复杂查询** (JOIN) | < 100ms | < 500ms | 2-3 表 JOIN |
| **聚合查询** (GROUP BY) | < 500ms | < 2000ms | 统计查询 |
| **慢查询** | < 1秒 | < 5秒 | 需要优化 |

**优化建议**:
- P95 > 100ms：添加索引
- P95 > 500ms：重构查询
- P99 > 5秒：标记为慢查询，优化

### 数据库资源使用

| 资源 | 基线 | 说明 |

| **CPU 使用率** | < 70% | 数据库服务器 |
| **内存使用率** | < 80% | InnoDB Buffer Pool |

## 🧪 性能测试场景

### 1. 负载测试 (Load Test)

**目标**: 验证系统在正常负载下的性能

**配置**:
- 虚拟用户: 10 → 100
- 持续时间: 5 分钟
- 加载策略: 阶梯式增长

**性能基线**:
- P95 响应时间: < 500ms
- P99 响应时间: < 1000ms
- 错误率: < 1%

**执行命令**:
```bash
k6 run tests/performance/performance_test.js
```

### 2. 压力测试 (Stress Test)

**目标**: 找到系统性能瓶颈和极限

**配置**:
- 虚拟用户: 100 → 300
- 持续时间: 16 分钟
- 加载策略: 阶梯式增长，保持峰值

**性能基线** (压力测试阈值更宽松):
- P95 响应时间: < 3000ms
- 错误率: < 10%

**观察指标**:
- 系统何时开始出现错误
- 响应时间何时急剧上升
- CPU/内存使用率峰值

### 3. 浸泡测试 (Soak Test)

**目标**: 验证系统长时间运行的稳定性

**配置**:
- 虚拟用户: 50
- 持续时间: 1 小时
- 加载策略: 预热 → 持续 → 降温

**性能基线**:
- P95 响应时间: < 1000ms
- 错误率: < 1%

**观察指标**:
- 内存泄漏（内存使用持续上升）
- 连接泄漏（数据库连接数持续上升）
- 性能退化（响应时间逐渐变慢）

### 4. 峰值测试 (Spike Test)

**目标**: 验证系统应对突发流量的能力

**配置**:
- 虚拟用户: 100 → 1000
- 持续时间: 4 分钟
- 加载策略: 快速爬坡 → 保持 → 快速降压

**性能基线** (峰值测试允许降级):
- P95 响应时间: < 5000ms
- 错误率: < 20%

**观察指标**:
- 系统是否崩溃
- 自动扩缩容是否生效
- 限流机制是否触发

## 🔧 性能优化建议

### 1. API 性能优化

**优化前**:
```go
// N+1 查询问题
bots, _ := db.Where("tenant_id = ?", tenantID).Find(&bots)
for _, bot := range bots {
    var config BotConfig
    db.Where("bot_id = ?", bot.BotID).First(&config) // N+1 查询
}
```

**优化后**:
```go
// 使用 Preload 预加载
var bots []Bot
db.Preload("Config").Where("tenant_id = ?", tenantID).Find(&bots)
```

**效果**:
- 查询次数: 1 + N → 1
- 响应时间: 500ms → 50ms

### 2. 缓存优化

**Redis 缓存策略**:
```go
// 缓存租户信息，TTL 5 分钟
cacheKey := fmt.Sprintf("tenant:%s", tenantID)
tenant, err := redis.Get(cacheKey)
if err != nil {
    // 缓存未命中，查询数据库
    tenant, err := db.GetTenant(tenantID)
    redis.Set(cacheKey, tenant, 5*time.Minute)
}
```

**缓存命中率基线**:
- 租户信息缓存: > 90%
- 权限检查缓存: > 95%
- 配额检查缓存: > 95%

### 3. 数据库优化

**索引优化**:
```sql
-- 添加复合索引
CREATE INDEX idx_tenant_status_created
ON bots(tenant_id, status, created_at);

-- 效果：查询性能提升 10x
```

**查询优化**:
```sql
-- 优化前（全表扫描）
SELECT * FROM bots WHERE tenant_id = 'xxx' AND status = 'active';

-- 优化后（使用索引）
SELECT bot_id, name, status
FROM bots
WHERE tenant_id = 'xxx' AND status = 'active';
```

### 4. 并发优化

**限制并发数**:
```go
// 使用信号量限制并发
sem := make(chan struct{}, 10)
var wg sync.WaitGroup

for _, id := range botIDs {
    wg.Add(1)
    sem <- struct{}{}
    go func(botID string) {
        defer wg.Done()
        defer func() { <-sem }()
        processBot(botID)
    }(id)
}
wg.Wait()
```
