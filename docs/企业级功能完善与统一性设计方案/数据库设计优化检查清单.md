## 1. 表设计检查

### 1.1 基础规范

- [ ] **主键设计**
  - [ ] 每个表都有主键(`id BIGINT PRIMARY KEY AUTO_INCREMENT`)
  - [ ] 主键使用`BIGINT`而非`INT`(支持未来扩展)
  - [ ] 主键使用`AUTO_INCREMENT`或全局ID生成器

- [ ] **字段命名**
  - [ ] 表名: 小写+下划线+复数形式(bot_conversations)
  - [ ] 字段名: 小写+下划线(user_id, created_at)
  - [ ] 布尔字段: `is_`前缀(is_active, is_deleted)
  - [ ] 时间字段: `_at`后缀(created_at, updated_at)
  - [ ] 外键字段: `_id`后缀(bot_id, user_id)
  - [ ] ❌ 无驼峰命名(userID, createTime)

- [ ] **数据类型**
  - [ ] 主键/外键: `BIGINT`
  - [ ] 状态枚举: `TINYINT`或`ENUM`
  - [ ] 金额字段: `DECIMAL(10,2)`而非`FLOAT/DOUBLE`
  - [ ] JSON配置: `JSON`类型(MySQL 5.7+)
  - [ ] 长文本: `TEXT`而非`VARCHAR(10000)`
  - [ ] ❌ 无过度使用VARCHAR(如VARCHAR(10000))

- [ ] **字段约束**
  - [ ] 重要字段添加`NOT NULL`约束
  - [ ] 为字段设置合理的默认值(DEFAULT)
  - [ ] 业务唯一性添加`UNIQUE`约束
  - [ ] 外键关系添加`FOREIGN KEY`约束
  - [ ] 使用`CHECK`约束验证数据(MySQL 8.0+)

- [ ] **审计字段**
  - [ ] 添加`created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP`
  - [ ] 添加`updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`
  - [ ] 软删除表添加`deleted_at DATETIME DEFAULT NULL`
  - [ ] 多租户表添加`tenant_id VARCHAR(64) NOT NULL`

- [ ] **注释**
  - [ ] 每个表有`COMMENT`说明用途
  - [ ] 每个字段有`COMMENT`说明含义
  - [ ] 枚举值有注释说明(如status字段)
  - [ ] 反范式化字段注释说明冗余原因

### 1.2 范式化检查

- [ ] **第一范式(1NF)**: 字段原子性
  - [ ] ❌ 无逗号分隔的多值字段(如emails用逗号分隔)
  - [ ] ✅ 一对多关系使用单独表存储

- [ ] **第二范式(2NF)**: 消除部分依赖
  - [ ] 复合主键表检查非主键字段是否完全依赖主键
  - [ ] 部分依赖的字段拆分到关联表

- [ ] **第三范式(3NF)**: 消除传递依赖
  - [ ] ❌ 无传递依赖(如users表包含city_name,应通过city_id关联)
  - [ ] 传递依赖字段拆分到关联表

- [ ] **反范式化评估**
  - [ ] 读多写少场景?(读写比>10:1)
  - [ ] 冗余字段有明确的业务理由
  - [ ] 有数据一致性维护方案(触发器/应用层)
  - [ ] 冗余字段有详细注释

## 2. 索引设计检查

### 2.1 索引创建

- [ ] **主键索引**
  - [ ] 每个表都有主键索引

- [ ] **外键索引**
  - [ ] 所有外键字段都有索引
  - [ ] 索引命名: `idx_外键名`

- [ ] **唯一索引**
  - [ ] 业务唯一性字段有`UNIQUE`索引
  - [ ] 索引命名: `uk_字段名`

- [ ] **单列索引**
  - [ ] WHERE条件字段有索引
  - [ ] ORDER BY字段有索引(高频查询)
  - [ ] JOIN字段有索引

- [ ] **复合索引**
  - [ ] 复合索引符合最左前缀原则
  - [ ] 等值查询列在前,范围查询列在后
  - [ ] 索引列顺序合理(高选择性列在前)

- [ ] **覆盖索引**
  - [ ] 高频查询创建覆盖索引(避免回表)
  - [ ] 覆盖索引包含SELECT所需的所有列

### 2.2 索引评估

- [ ] **索引选择性**
  - [ ] 计算索引选择性: `COUNT(DISTINCT col) / COUNT(*)`
  - [ ] 选择性>0.9: 优秀
  - [ ] 选择性0.7-0.9: 良好
  - [ ] 选择性<0.1: 不建议建索引(如gender)

- [ ] **冗余索引检查**
  - [ ] `idx_a_b`和`idx_a`同时存在时,后者可删除
  - [ ] 检查重复索引

- [ ] **索引数量**
  - [ ] 单表索引数量<5个(避免过多影响写入性能)
  - [ ] 总索引大小<表数据大小/3

### 2.3 索引失效风险

- [ ] **避免索引失效**
  - [ ] ❌ WHERE中使用函数: `WHERE DATE(created_at) = '2025-01-30'`
  - [ ] ✅ 改用范围查询: `WHERE created_at >= '2025-01-30' AND created_at < '2025-01-31'`
  - [ ] ❌ 隐式类型转换: `WHERE phone = 13800138000`(phone是VARCHAR)
  - [ ] ❌ 前缀模糊查询: `WHERE name LIKE '%张'`
  - [ ] ❌ 负向查询: `WHERE status != 1`

## 3. 表关系检查

- [ ] **外键约束**
  - [ ] 关联关系使用`FOREIGN KEY`约束
  - [ ] 级联策略合理:`ON DELETE CASCADE`/`SET NULL`/`RESTRICT`
  - [ ] 外键字段有索引

- [ ] **关系设计**
  - [ ] 一对一: 关联表有`UNIQUE`约束
  - [ ] 一对多: 外键在"多"方表
  - [ ] 多对多: 使用中间表,复合唯一索引

- [ ] **避免循环依赖**
  - [ ] ❌ A依赖B, B依赖C, C依赖A(循环依赖)

## 4. 性能优化检查

### 4.1 表大小评估

- [ ] **单表数据量**
  - [ ] 当前数据量<2000万行
  - [ ] 预估1年数据量<5000万行
  - [ ] 单表数据文件<10GB

- [ ] **分表评估**
  - [ ] [ ] 如超过阈值,制定分表方案
  - [ ] 日志类表按时间分表
  - [ ] 历史数据归档策略

### 4.2 查询性能

- [ ] **慢查询风险评估**
  - [ ] 无全表扫描查询
  - [ ] 无大结果集查询(>10000行)
  - [ ] 无深分页查询(LIMIT 1000000, 20)

- [ ] **JOIN优化**
  - [ ] 小表驱动大表
  - [ ] JOIN字段有索引
  - [ ] 避免多表JOIN(>5个表)

## 🔧 工具脚本

### 检查表设计规范
```sql
-- 检查表是否有主键
SELECT
    TABLE_NAME,
    CASE
        WHEN TABLE_COMMENT = '' OR TABLE_COMMENT IS NULL THEN '❌ 缺少表注释'
        ELSE '✅ 有表注释'
    END AS check_comment,
    CASE
        WHEN TABLE_ROWS > 20000000 THEN '⚠️ 数据量>2000万,建议分表'
        ELSE '✅ 数据量合理'
    END AS check_rows,
    ROUND((DATA_LENGTH + INDEX_LENGTH) / 1024 / 1024, 2) AS size_mb
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'coze_studio'
  AND TABLE_TYPE = 'BASE TABLE'
ORDER BY (DATA_LENGTH + INDEX_LENGTH) DESC;
```

-- 检查未使用的索引

## 附录

### A. 常见错误示例

```sql
-- ❌ 错误1: 违反1NF
CREATE TABLE users_bad (
    id BIGINT PRIMARY KEY,
    name VARCHAR(255),
    emails VARCHAR(1000)  -- 多个邮箱用逗号分隔
);

-- ✅ 正确: 一对多关系表
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name VARCHAR(255)
);
CREATE TABLE user_emails (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    email VARCHAR(255) NOT NULL,
    FOREIGN KEY (user_id) REFERENCES users(id)
);

-- ❌ 错误2: 违反2NF
CREATE TABLE order_items_bad (
    order_id BIGINT,
    product_id BIGINT,
    product_name VARCHAR(255),  -- 依赖于product_id
    quantity INT,
    PRIMARY KEY (order_id, product_id)
);

-- ✅ 正确: 拆分表
CREATE TABLE order_items (
    id BIGINT PRIMARY KEY,
    order_id BIGINT,
    product_id BIGINT,
    quantity INT,
    price DECIMAL(10,2),  -- 快照价格
    FOREIGN KEY (product_id) REFERENCES products(id)
);

-- ❌ 错误3: 违反3NF
CREATE TABLE users_bad (
    id BIGINT PRIMARY KEY,
    name VARCHAR(255),
    city_id BIGINT,
    city_name VARCHAR(100),  -- 传递依赖
    province_name VARCHAR(100)
);

-- ✅ 正确: 规范化
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name VARCHAR(255),
    city_id BIGINT,
    FOREIGN KEY (city_id) REFERENCES cities(id)
);
```

### B. 最佳实践模板

```sql
-- ✅ 最佳实践: 完整的表设计
CREATE TABLE bot_conversations (
    -- 主键
    id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '会话ID',

    -- 租户隔离
    tenant_id VARCHAR(64) NOT NULL COMMENT '租户ID',

    -- 业务字段
    bot_id BIGINT NOT NULL COMMENT 'Bot ID',
    user_id BIGINT NOT NULL COMMENT '用户ID',
    title VARCHAR(255) DEFAULT '新对话' COMMENT '对话标题',

    -- 统计字段(反范式化,避免JOIN)
    message_count INT DEFAULT 0 COMMENT '消息数量',
    token_used INT DEFAULT 0 COMMENT 'Token使用量',

    -- 状态字段
    status ENUM('active', 'archived', 'deleted') DEFAULT 'active' COMMENT '状态',

    -- 软删除
    deleted_at DATETIME DEFAULT NULL COMMENT '删除时间',

    -- 审计字段
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',

    -- 索引
    UNIQUE KEY uk_tenant_user (tenant_id, user_id, deleted_at),  -- 联合唯一
    INDEX idx_bot_id (bot_id),                                   -- 外键索引
    INDEX idx_user_id (user_id),
    INDEX idx_status_created (status, created_at DESC),          -- 复合索引(状态+时间排序)
    INDEX idx_tenant_id (tenant_id),

    -- 外键约束
    FOREIGN KEY (bot_id) REFERENCES bots(id) ON DELETE CASCADE,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE

) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='Bot对话表';
```
