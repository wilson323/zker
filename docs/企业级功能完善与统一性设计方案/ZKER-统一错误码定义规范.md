## 错误码设计原则

### 1.1 设计理念

**统一性**: 所有模块使用统一的错误码格式和命名规范
**可读性**: 错误码具有自描述性，开发者能快速理解错误类型和原因
**扩展性**: 预留足够的扩展空间，支持未来新增模块和错误类型
**国际化**: 支持多语言错误提示，便于国际化部署
**可追溯性**: 每个错误码对应唯一的错误描述和处理建议

### 1.2 核心原则

- ✅ **结构化**: 采用分层结构，便于模块化管理
- ✅ **语义化**: 错误码本身携带模块、类型、严重程度信息
- ✅ **一致性**: 相同的错误场景使用相同的错误码
- ✅ **版本化**: 错误码定义纳入版本管理，保持向后兼容
- ✅ **文档化**: 所有错误码必须记录在文档中，包括处理建议

## 错误码格式规范

### 2.1 标准格式

```
格式: {模块前缀}{错误类型}{三位数字}
示例: AUTH001, BOT404, TARG500
```

**组成部分**:

1. **模块前缀** (2-4 位大写字母)
   - 标识发生错误的模块
   - 详见 [模块前缀清单](#23-模块前缀清单)

2. **错误类型** (1 位数字)
   - 标识错误的严重程度和类型
   - 详见 [错误类型定义](#22-错误类型定义)

3. **三位数字** (001-999)
   - 同一模块内同一类型错误的具体编号
   - 建议按功能模块或错误场景分组

### 2.2 错误类型定义

| 错误类型 | 数字 | 说明 | HTTP 状态码 | 示例 |
|---------|------|------|------------|------|
| **成功** | 0 | 请求成功 | 200 OK | SUCCESS |
| **客户端错误** | 1 | 客户端请求参数错误 | 400 Bad Request | AUTH100 |
| **认证授权错误** | 2 | 认证失败或权限不足 | 401/403 | AUTH201 |
| **资源未找到** | 3 | 请求的资源不存在 | 404 Not Found | BOT301 |
| **业务逻辑错误** | 4 | 业务规则校验失败 | 422 Unprocessable Entity | ORD401 |
| **冲突错误** | 5 | 资源冲突或并发冲突 | 409 Conflict | TARG501 |
| **限流错误** | 6 | 请求频率超限 | 429 Too Many Requests | API601 |
| **服务端错误** | 5 | 服务器内部错误 | 500 Internal Server Error | SYS500 |
| **服务不可用** | 6 | 服务依赖故障或维护中 | 503 Service Unavailable | SVC501 |
| **超时错误** | 7 | 请求处理超时 | 504 Gateway Timeout | API701 |

## 错误码分类体系

### 3.1 按严重程度分类

**P0 - 严重错误**:
- 系统崩溃、数据丢失
- 服务完全不可用
- 需要立即处理
- 示例: SYS500, DB500

**P1 - 高优先级错误**:
- 核心功能不可用
- 影响大量用户
- 需要快速响应
- 示例: AUTH500, BOT500

**P2 - 中优先级错误**:
- 部分功能异常
- 影响少量用户
- 需要尽快处理
- 示例: CONV401, KNW301

**P3 - 低优先级错误**:
- 边缘场景错误
- 不影响主流程
- 可计划处理
- 示例: MON301, AGN301

### 3.2 按错误来源分类

**客户端错误 (4xx)**:
- 参数错误
- 认证失败
- 权限不足
- 资源不存在
- 业务规则校验失败

**服务端错误 (5xx)**:
- 内部错误
- 依赖服务故障
- 超时
- 资源耗尽

## HTTP 状态码映射

### 5.1 完整映射表

| HTTP 状态码 | 错误类型范围 | 说明 |
|------------|------------|------|
| **200 OK** | SUCCESS | 请求成功 |
| **400 Bad Request** | 1xx | 客户端请求参数错误 |
| **401 Unauthorized** | 2xx | 认证失败 |
| **403 Forbidden** | 3xx | 权限不足 |
| **404 Not Found** | 3xx | 资源不存在 |
| **409 Conflict** | 5xx | 资源冲突 |
| **415 Unsupported Media Type** | 1xx | 不支持的媒体类型 |
| **422 Unprocessable Entity** | 4xx | 业务逻辑错误 |
| **429 Too Many Requests** | 6xx | 请求频率超限 |
| **500 Internal Server Error** | 5xx | 服务端内部错误 |
| **503 Service Unavailable** | 5xx/6xx | 服务不可用 |
| **504 Gateway Timeout** | 7xx | 网关或服务超时 |

### 5.2 状态码使用规范

**2xx 成功**:
- 仅用于请求完全成功的情况
- 业务逻辑错误不应使用 2xx

**4xx 客户端错误**:
- 客户端请求参数、格式、逻辑错误
- 不应重试，除非修改请求

**5xx 服务端错误**:
- 服务端内部错误、依赖服务故障
- 可以重试

package middleware

import (
    "github.com/cloudwego/hertz/pkg/app"
    "github.com/coze-studio/pkg/errors"
)

func ErrorHandler() app.HandlerFunc {
    return func(ctx context.Context, c *app.RequestContext) {
        c.Next(ctx)

        if len(c.Errors) > 0 {
            err := c.Errors.Last()

            if appErr, ok := err.Err.(*errors.AppError); ok {
                c.JSON(appErr.StatusCode, appErr)
            } else {

                    "code":    "SYS500",
                    "message": "系统内部错误",
                })
            }
        }
    }
}

### 7.2 前端错误处理

**统一错误处理函数**:
```typescript
// src/utils/error-handler.ts
import { getErrorMessage } from './errors';

export interface ApiError {
  code: string;
  message: string;
  message_zh?: string;
  message_en?: string;
  details?: Record<string, unknown>;
  request_id?: string;
  timestamp?: string;
}

export function handleApiError(error: ApiError, lang: string = 'zh'): void {
  const message = error[`message_${lang}`] || error.message || getErrorMessage(error.code, lang);

  switch (error.code) {
    case 'AUTH200':
    case 'AUTH201':
      // 认证错误，跳转登录页
      window.location.href = '/login';
      break;

    case 'AUTH300':
    case 'AUTH301':
      // 权限错误，显示提示
      toast.error(message);
      break;

    case 'API600':
    case 'API601':
      // 限流错误，提示稍后重试
      toast.warning(message);
      break;

    default:
      // 其他错误，显示错误信息
      toast.error(message);
  }

  // 记录错误日志
  console.error('[API Error]', {
    code: error.code,
    message: error.message,
    request_id: error.request_id,
    timestamp: error.timestamp,
  });
}
```

## 错误码扩展指南

### 8.1 新增错误码流程

**步骤 1: 确定错误码结构**
```
格式: {模块前缀}{错误类型}{三位数字}
示例: NEWM401
```

**步骤 2: 检查错误码是否已存在**
- 查阅本文档 [完整错误码清单](#4-完整错误码清单)
- 确保新错误码不与已有错误码冲突

**步骤 3: 定义错误信息**
```json
{
  "code": "NEWM401",
  "message_zh": "中文错误描述",
  "message_en": "English error description",
  "http_status": 422,
  "severity": "P2",
  "handling_suggestion": "处理建议"
}
```

**步骤 4: 更新文档**
- 在本文档对应模块的错误码清单中添加新错误码
- 更新错误信息对照表

**步骤 5: 实现错误处理**
- 后端: 在 `pkg/errors/` 中添加错误定义
- 前端: 在 `src/utils/errors.ts` 中添加错误信息

### 8.2 错误码命名规范

**模块前缀命名**:
- 使用大写字母
- 长度 2-4 位
- 与模块名称相关
- 示例: AUTH, USER, BOT

**错误类型选择**:
- 0: 成功
- 1: 客户端错误
- 2: 认证授权错误
- 3: 资源未找到
- 4: 业务逻辑错误
- 5: 冲突/服务端错误
- 6: 限流/服务不可用
- 7: 超时错误

**数字编号规则**:
- 001-099: 通用错误
- 100-199: 参数相关错误
- 200-299: 认证相关错误
- 300-399: 资源相关错误
- 400-499: 业务逻辑错误
- 500-599: 系统错误

### 8.3 错误码废弃流程

**步骤 1: 标记为废弃**
- 在文档中添加 `@deprecated` 标记
- 说明废弃原因和替代错误码

**步骤 2: 设置过渡期**
- 至少保留 6 个月的过渡期
- 过渡期内保持向后兼容

**步骤 3: 移除废弃错误码**
- 在过渡期结束后移除
- 更新相关代码和文档

### 附录B: 错误严重程度分级

**P0 - 严重错误 (Critical)**:
- 定义: 系统完全不可用或数据丢失
- 响应时间: 立即 (15 分钟内)
- 处理团队: 核心开发团队
- 示例: SYS500, DB500

**P1 - 高优先级错误 (High)**:
- 定义: 核心功能不可用或影响大量用户
- 响应时间: 1 小时内
- 处理团队: 模块负责人
- 示例: AUTH500, BOT500

**P2 - 中优先级错误 (Medium)**:
- 定义: 部分功能异常或影响少量用户
- 响应时间: 4 小时内
- 处理团队: 模块开发人员
- 示例: CONV401, KNW301

**P3 - 低优先级错误 (Low)**:
- 定义: 边缘场景错误或不影响主流程
- 响应时间: 1 个工作日内
- 处理团队: 按排期处理
- 示例: MON301, AGENT301

### 附录C: 错误码使用示例

**Go 后端使用示例**:
```go
// internal/service/user_service.go
package service

import (
    "github.com/coze-studio/pkg/errors"
)

func (s *UserService) GetUser(userID string) (*User, error) {
    user, err := s.repo.FindByID(userID)
    if err != nil {
        if errors.Is(err, gorm.ErrRecordNotFound) {
            return nil, errors.NewUserError(
                "USER300",
                "用户不存在",
                map[string]interface{}{
                    "user_id": userID,
                },
            )
        }
        return nil, errors.NewInternalError("SYS502", "数据库错误")
    }
    return user, nil
}
```
