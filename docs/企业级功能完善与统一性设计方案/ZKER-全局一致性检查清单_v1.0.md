# ZKER 全局一致性检查清单 v1.0

> **文档目的**: 本文档提供了一套系统化的全局一致性检查工具，确保4位开发人员在并行开发过程中始终保持代码、架构、数据和接口的全局一致性。
>
> **适用范围**: 所有开发人员在代码提交、PR创建、功能集成前必须完成相应级别的一致性检查
>
> **检查频率**:
> - 开发阶段：每日至少执行一次个人检查清单
> - 提交阶段：每次代码提交前执行提交前检查
> - 集成阶段：每周执行团队交叉检查
> - 发布阶段：每次版本发布前执行发布前检查

---

## 📋 检查清单使用指南

### 检查级别说明

| 级别 | 适用场景 | 检查范围 | 执行者 |
|------|---------|---------|--------|
| **L1 - 个人检查** | 日常开发 | 代码风格、命名规范、基础逻辑 | 开发人员本人 |
| **L2 - 模块检查** | 提交前 | 模块间接口、数据一致性、API契约 | 开发人员本人 + Code Reviewer |
| **L3 - 集成检查** | 功能集成 | 跨模块集成、端到端流程、性能影响 | 技术负责人 + 全体开发 |
| **L4 - 发布检查** | 版本发布 | 完整性、安全性、向后兼容性 | 技术负责人 + DevOps + QA |

## 1. 代码一致性检查

### 1.1 后端代码一致性（Go）

#### L1 - 个人检查

- [ ] **命名规范检查**
  - [ ] 包名使用小写单数形式（如 `permission`，而非 `permissions`）
  - [ ] 文件名使用小写下划线分隔（如 `bot_service.go`，而非 `botService.go`）
  - [ ] 常量使用大写下划线分隔（如 `MAX_BOT_COUNT`）
  - [ ] 接口名以 `er` 结尾（如 `BotRepository`）
  - [ ] 私有变量使用小驼峰（如 `botID`）
  - [ ] 公共导出变量使用大驼峰（如 `BotService`）

- [ ] **函数设计检查**
  - [ ] 单个函数不超过 50 行
  - [ ] 函数参数不超过 5 个（超过时使用 struct 封装）
  - [ ] 函数只做一件事（单一职责原则）
  - [ ] 函数名称清晰表达意图（动词开头，如 `CreateBot`、`ValidateUser`）
  - [ ] 错误处理使用 `%w` 包装错误链

- [ ] **DDD 分层检查**
  - [ ] `domain/` 层：只包含业务逻辑，无基础设施依赖
  - [ ] `application/` 层：编排领域服务，处理事务边界
  - [ ] `api/` 层：只处理 HTTP 请求/响应，无业务逻辑
  - [ ] `infra/` 层：实现基础设施接口，无业务逻辑

- [ ] **错误处理检查**
  - [ ] 所有错误都使用统一错误码（参考 `ZKER-统一错误码定义规范.md`）
  - [ ] 错误消息包含中英文双语
  - [ ] 错误日志包含上下文信息（request_id、user_id、tenant_id）
  - [ ] 不使用 `panic`，使用 `error` 返回

#### L2 - 模块检查

- [ ] **接口一致性检查**
  - [ ] 接口定义在 `domain/` 层，实现在 `infra/` 层
  - [ ] 接口方法命名统一（如 `GetByID`、`Create`、`Update`、`Delete`）
  - [ ] 接口参数使用 DTO（Data Transfer Object）
  - [ ] 接口返回值统一格式（`(*T, error)`）

- [ ] **依赖方向检查**
  - [ ] 依赖关系单向：`api/` → `application/` → `domain/` ← `infra/`
  - [ ] `domain/` 层不依赖任何外层
  - [ ] 使用依赖注入而非直接实例化

- [ ] **并发安全检查**
  - [ ] 共享变量使用 `sync.Mutex` 或 `sync.RWMutex` 保护
  - [ ] Goroutine 数量受控（使用 semaphore 限制并发数）
  - [ ] Channel 使用有缓冲避免阻塞
  - [ ] Context 正确传递和取消

#### L3 - 集成检查

- [ ] **跨模块调用检查**
  - [ ] 模块间调用使用接口而非具体实现
  - [ ] 模块间数据传输使用 DTO
  - [ ] 循环依赖检查（使用 `go mod graph` 检查）
  - [ ] 模块边界清晰，无越层调用

### 1.2 前端代码一致性（React + TypeScript）

#### L1 - 个人检查

- [ ] **命名规范检查**
  - [ ] 组件文件使用大驼峰（如 `MessageBox.tsx`）
  - [ ] 工具文件使用小驼峰（如 `formatUtils.ts`）
  - [ ] 类型定义文件使用 `.types.ts` 后缀（如 `bot.types.ts`）
  - [ ] 常量使用大写下划线（如 `MAX_MESSAGE_COUNT`）
  - [ ] 接口使用 `I` 前缀或直接 `interface`（如 `IBotConfig` 或 `BotConfig`）

- [ ] **组件设计检查**
  - [ ] 单个组件不超过 300 行
  - [ ] 组件只做一件事（单一职责）
  - [ ] Props 接口清晰定义（使用 TypeScript interface）
  - [ ] 使用函数式组件 + Hooks，不使用类组件
  - [ ] 组件名称使用大驼峰

- [ ] **TypeScript 类型检查**
  - [ ] 所有变量都有明确的类型定义
  - [ ] 避免使用 `any`，使用 `unknown` 代替
  - [ ] 函数返回值类型明确
  - [ ] Props 和 State 都有类型定义
  - [ ] 启用 `strict` 模式

- [ ] **React Hooks 检查**
  - [ ] `useState` 正确使用（不直接修改 state）
  - [ ] `useEffect` 依赖数组完整
  - [ ] `useCallback` 和 `useMemo` 优化性能
  - [ ] 自定义 Hooks 使用 `use` 前缀（如 `useBotList`）

#### L2 - 模块检查

- [ ] **组件层次检查**
  - [ ] 组件树深度不超过 5 层
  - [ ] Props drilling 不超过 3 层
  - [ ] 使用 Context 或 Zustand 管理全局状态
  - [ ] 组件职责清晰（展示组件 vs 容器组件）

- [ ] **状态管理检查**
  - [ ] 局部状态使用 `useState`
  - [ ] 跨组件状态使用 Zustand store
  - [ ] 服务端状态使用 React Query / SWR
  - [ ] 表单状态使用 React Hook Form

#### L3 - 集成检查

- [ ] **包依赖检查**
  - [ ] Rush.js 包依赖关系正确（无循环依赖）
  - [ ] 使用 `workspace:` 协议引用内部包
  - [ ] 包的公共 API 通过 `src/index.ts` 导出
  - [ ] 包之间不直接引用内部文件

## 2. 架构一致性检查

### 2.1 DDD 分层架构检查

#### L1 - 个人检查

- [ ] **目录结构检查**
  ```
  backend/
  ├── api/              # HTTP 处理器
  │   └── v1/          # API 版本
  ├── application/      # 应用服务
  │   └── dto/         # 数据传输对象
  ├── domain/          # 领域层
  │   ├── entity/      # 实体
  │   ├── repository/  # 仓储接口
  │   └── service/     # 领域服务
  └── infra/           # 基础设施
      ├── repository/  # 仓储实现
      └── client/      # 外部客户端
  ```

- [ ] **职责划分检查**
  - [ ] `api/`：只处理 HTTP 协议转换
  - [ ] `application/`：编排用例，管理事务
  - [ ] `domain/`：核心业务逻辑
  - [ ] `infra/`：技术实现细节

#### L2 - 模块检查

- [ ] **依赖方向检查**
  - [ ] `api/` 依赖 `application/`
  - [ ] `application/` 依赖 `domain/`
  - [ ] `infra/` 实现 `domain/` 定义的接口
  - [ ] `domain/` 不依赖任何其他层

#### L3 - 集成检查

- [ ] **领域边界检查**
  - [ ] 每个领域模块独立（如 `bot/`、`workflow/`、`knowledge/`）
  - [ ] 领域间通过接口通信
  - [ ] 领域内高内聚，领域间低耦合
  - [ ] 跨领域业务逻辑放在 `application/` 层

---

### 2.2 微服务边界检查

#### L2 - 模块检查

- [ ] **服务拆分检查**
  - [ ] 按业务领域拆分服务（Bot 服务、Workflow 服务、Knowledge 服务）
  - [ ] 服务之间通过 API 或消息队列通信
  - [ ] 每个服务独立部署
  - [ ] 服务拥有独立数据库

- [ ] **通信方式检查**
  - [ ] 同步调用使用 RESTful API
  - [ ] 异步事件使用消息队列（NSQ/Kafka/Pulsar）
  - [ ] 事件命名使用过去式（如 `BotCreatedEvent`）

#### L4 - 发布检查

- [ ] **版本兼容性检查**
  - [ ] API 使用版本号（如 `/api/v1/bots`）
  - [ ] 向后兼容性检查（不删除字段，只添加可选字段）
  - [ ] 废弃 API 提前通知（至少 2 个版本周期）

## 3. 数据一致性检查

### 3.1 数据库设计一致性

#### L1 - 个人检查

- [ ] **表命名检查**
  - [ ] 表名使用小写复数形式（如 `bots`、`users`、`roles`）
  - [ ] 表名前缀使用领域名称（如 `bot_`、`workflow_`）
  - [ ] 关联表使用 `_` 连接两个表名（如 `bot_tags`）

- [ ] **字段命名检查**
  - [ ] 主键命名为 `{table}_id`（如 `bot_id`、`user_id`）
  - [ ] 外键命名为 `{referenced_table}_id`（如 `tenant_id`、`creator_id`）
  - [ ] 布尔字段使用 `is_` 前缀（如 `is_active`、`is_public`）
  - [ ] 时间字段使用 `_at` 后缀（如 `created_at`、`updated_at`）
  - [ ] 字段名使用小写下划线分隔

- [ ] **字段类型检查**
  - [ ] 主键使用 `VARCHAR(36)` 存储 UUID
  - [ ] 金额使用 `DECIMAL` 类型，不使用 `FLOAT`
  - [ ] 枚举使用 `ENUM` 类型
  - [ ] JSON 数据使用 `JSON` 类型
  - [ ] 时间使用 `TIMESTAMP` 类型

#### L2 - 模块检查

- [ ] **索引设计检查**
  - [ ] 外键字段都有索引
  - [ ] 常用查询条件都有索引
  - [ ] 联合索引遵循最左前缀原则
  - [ ] 索引命名规范：`idx_{field1}_{field2}`（如 `idx_tenant_status`）
  - [ ] 唯一索引命名：`uk_{field1}_{field2}`（如 `uk_tenant_name`）

- [ ] **约束检查**
  - [ ] 主键约束：所有表都有主键
  - [ ] 外键约束：关联关系正确建立
  - [ ] 唯一约束：业务唯一性字段有唯一索引
  - [ ] 非空约束：必填字段设置 `NOT NULL`

#### L3 - 集成检查

- [ ] **跨表数据一致性**
  - [ ] 使用事务保证多表操作的原子性
  - [ ] 软删除（`deleted_at`）在关联查询中正确过滤
  - [ ] 级联删除正确配置（`ON DELETE CASCADE`）
  - [ ] 冗余字段通过事件或定时任务同步

  - [ ] 索引正确创建

#### L4 - 发布检查

- [ ] **生产迁移检查**
  - [ ] 迁移在测试环境验证通过
  - [ ] 有回滚方案
  - [ ] 有数据备份
  - [ ] 迁移时间窗口选择在低峰期

### 3.3 多租户数据隔离检查

#### L2 - 模块检查

- [ ] **租户隔离检查**
  - [ ] 所有表都有 `tenant_id` 字段（除系统配置表）
  - [ ] 所有查询都添加 `tenant_id` 过滤条件
  - [ ] 所有插入都设置 `tenant_id`

- [ ] **配额限制检查**
  - [ ] 租户资源配额正确配置（Bot 数量、消息数量）
  - [ ] 超配额操作被拒绝并返回明确错误码
  - [ ] 配额使用量实时统计（使用计数器）

## 4. API 一致性检查

### 4.1 RESTful API 设计检查

#### L1 - 个人检查

- [ ] **URL 设计检查**
  - [ ] 使用小写字母和连字符（如 `/api/v1/bot-configs`）
  - [ ] 使用名词复数（如 `/bots`，而非 `/bot`）
  - [ ] 层级不超过 3 层（如 `/api/v1/tenants/:tenant_id/bots/:bot_id/conversations`）
  - [ ] 查询参数使用小驼峰（如 `?pageToken=xxx&pageSize=10`）

- [ ] **HTTP 方法检查**
  - [ ] `GET`：查询，幂等
  - [ ] `POST`：创建，非幂等
  - [ ] `PUT`：完整更新，幂等
  - [ ] `PATCH`：部分更新，幂等
  - [ ] `DELETE`：删除，幂等

- [ ] **状态码检查**
  - [ ] `200 OK`：成功
  - [ ] `201 Created`：创建成功
  - [ ] `204 No Content`：删除成功
  - [ ] `400 Bad Request`：参数错误
  - [ ] `401 Unauthorized`：未认证
  - [ ] `403 Forbidden`：无权限
  - [ ] `404 Not Found`：资源不存在
  - [ ] `409 Conflict`：资源冲突
  - [ ] `500 Internal Server Error`：服务器错误

#### L2 - 模块检查

- [ ] **请求格式检查**
  - [ ] 使用 `Content-Type: application/json`
  - [ ] 请求体通过 DTO 验证
  - [ ] 必填字段校验（`validation` tag）
  - [ ] 字段格式校验（邮箱、URL、UUID）

- [ ] **响应格式检查**
  ```json
  {
    "code": "SUCCESS",
    "message": "操作成功",
    "message_zh": "操作成功",
    "message_en": "Operation successful",
    "data": {
      "bot_id": "bot_123"
    },
    "request_id": "req_1234567890",
    "timestamp": "2025-01-01T12:00:00Z"
  }
  ```

- [ ] **错误响应检查**
  ```json
  {
    "code": "BOT_NOT_FOUND",
    "message": "Bot不存在",
    "message_zh": "Bot不存在",
    "message_en": "Bot not found",
    "details": {
      "bot_id": "bot_123"
    },
    "request_id": "req_1234567890",
    "timestamp": "2025-01-01T12:00:00Z"
  }
  ```

#### L3 - 集成检查

- [ ] **API 版本管理检查**
  - [ ] URL 中包含版本号（如 `/api/v1/`）
  - [ ] 重大变更时递增版本号（v1 → v2）
  - [ ] 旧版本保留至少 6 个月
  - [ ] 废弃 API 在响应头添加 `Deprecated: true`

- [ ] **跨服务 API 调用检查**
  - [ ] 使用服务发现的客户端（不硬编码 URL）
  - [ ] 调用超时设置（如 5 秒）
  - [ ] 重试机制（最多 3 次，指数退避）
  - [ ] 熔断机制（失败率超过 50% 时熔断）

---

### 4.2 错误码一致性检查

#### L1 - 个人检查

- [ ] **错误码定义检查**
  - [ ] 错误码使用大写下划线分隔（如 `BOT_NOT_FOUND`）
  - [ ] 错误码唯一（全局唯一）

  - [ ] 包含上下文信息（如资源 ID）

#### L2 - 模块检查

- [ ] **错误处理一致性**
  - [ ] 所有错误都返回统一格式
  - [ ] 错误日志包含必要上下文
  - [ ] 敏感信息不暴露到错误消息（如密码、Token）
  - [ ] 错误堆栈只在开发环境返回
