## 1. 数据库范式化设计

### 1.1 范式化理论应用

#### 1.1.1 第一范式 (1NF) - 确保原子性

**定义**: 每个字段都是不可再分的最小数据单位。

**应用场景**:
```sql
-- ✅ 正确 - 符合1NF
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name VARCHAR(255),           -- 单一值
    email VARCHAR(255),           -- 单一值
    phone VARCHAR(20)             -- 单一值
);

-- ❌ 错误 - 违反1NF
CREATE TABLE users_bad (
    id BIGINT PRIMARY KEY,
    name VARCHAR(255),
    emails VARCHAR(500),           -- 多个邮箱用逗号分隔
    phones VARCHAR(500)            -- 多个电话用逗号分隔
);
```

**最佳实践**:
- ✅ 一对多关系使用单独的表存储
- ✅ 使用 JSON 字段存储非结构化数据(需谨慎)
- ✅ 避免在字段中存储逗号分隔的多个值

#### 1.1.2 第二范式 (2NF) - 消除部分依赖

**定义**: 非主键字段必须完全依赖于主键。

**应用场景**:
```sql
-- ❌ 错误 - 违反2NF (复合主键下的部分依赖)
CREATE TABLE order_items_bad (
    order_id BIGINT,
    product_id BIGINT,
    product_name VARCHAR(255),    -- 依赖于product_id,而非(order_id,product_id)
    product_price DECIMAL(10,2),  -- 依赖于product_id
    quantity INT,
    PRIMARY KEY (order_id, product_id)
);

-- ✅ 正确 - 符合2NF
CREATE TABLE order_items (
    id BIGINT PRIMARY KEY,
    order_id BIGINT,
    product_id BIGINT,
    quantity INT,
    price DECIMAL(10,2),          -- 下单时的快照价格
    created_at DATETIME,
    INDEX idx_order_id (order_id),
    FOREIGN KEY (product_id) REFERENCES products(id)
);

CREATE TABLE products (
    id BIGINT PRIMARY KEY,
    name VARCHAR(255),
    price DECIMAL(10,2),          -- 当前价格
    updated_at DATETIME
);
```

**最佳实践**:
- ✅ 复合主键时，确保所有非主键字段依赖于整个主键
- ✅ 将部分依赖的字段拆分到关联表中
- ✅ 使用快照机制存储历史数据(如order_items.price)

#### 1.1.3 第三范式 (3NF) - 消除传递依赖

**定义**: 非主键字段不传递依赖于主键。

**应用场景**:
```sql
-- ❌ 错误 - 违反3NF (传递依赖)
CREATE TABLE users_bad (
    id BIGINT PRIMARY KEY,
    name VARCHAR(255),
    city_id BIGINT,
    city_name VARCHAR(100),       -- 依赖于city_id,而非直接依赖于user.id
    province_name VARCHAR(100)    -- 依赖于city_id
);

-- ✅ 正确 - 符合3NF
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name VARCHAR(255),
    city_id BIGINT,
    created_at DATETIME,
    INDEX idx_city_id (city_id),
    FOREIGN KEY (city_id) REFERENCES cities(id)
);

CREATE TABLE cities (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100),
    province_id BIGINT,
    INDEX idx_province_id (province_id),
    FOREIGN KEY (province_id) REFERENCES provinces(id)
);
```

**最佳实践**:
- ✅ 消除传递依赖，建立规范的表关系
- ✅ 冗余字段必须有明确的业务理由(如性能优化)
- ✅ 使用视图(VIEW)或缓存层处理频繁的关联查询

#### 1.1.4 反范式化策略 (性能优化)

**定义**: 在满足3NF的基础上，有意识地引入冗余以提升性能。

**应用场景**:

**场景1: 读多写少 - 冗余统计字段**
```sql
-- ✅ 合理反范式化 - 冗余clone_count避免频繁JOIN
CREATE TABLE bot_store_listings (
    id BIGINT PRIMARY KEY,
    bot_id BIGINT NOT NULL,
    clone_count INT DEFAULT 0,        -- 冗余字段,提升查询性能

    -- 审计字段
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

    INDEX idx_clone_count (clone_count DESC)  -- 排行榜查询
);

-- 通过触发器或应用层维护clone_count
-- 避免每次查询都JOIN克隆记录表
```

**场景2: 缓存关联数据**
```sql
-- ✅ 合理反范式化 - 冗余tenant_name避免JOIN
CREATE TABLE bots (
    id BIGINT PRIMARY KEY,
    tenant_id VARCHAR(64) NOT NULL,
    tenant_name VARCHAR(255),        -- 冗余字段
    name VARCHAR(255),

    INDEX idx_tenant_name (tenant_name)
);

-- 通过应用层同步更新tenant_name
-- 提升按租户名搜索的性能
```

**反范式化决策树**:
```
是否需要反范式化?
  ├─ 是否为读多写少场景? (读写比 > 10:1)
  │    ├─ 是 → 继续评估
  │    └─ 否 → 保持3NF
  ├─ 性能问题是否无法通过索引优化解决?
  │    ├─ 是 → 考虑反范式化
  │    └─ 否 → 优先索引优化
  ├─ 冗余字段的数据一致性维护成本是否可接受?
  │    ├─ 是 → 可以反范式化
  │    └─ 否 → 保持3NF
  └─ 结论: 谨慎反范式化,必须详细注释说明原因
```

**最佳实践**:
- ✅ 冗余字段必须添加详细注释说明业务理由
- ✅ 通过触发器或应用层代码保证数据一致性
- ✅ 定期检查冗余数据的一致性
- ✅ 在文档中明确标注反范式化的字段

### 1.2 字段设计规范

#### 1.2.1 命名规范

```sql
-- ✅ 正确的命名规范
CREATE TABLE bot_conversations (
    id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '会话ID',
    tenant_id VARCHAR(64) NOT NULL COMMENT '租户ID',      -- 小写+下划线
    bot_id BIGINT NOT NULL COMMENT 'Bot ID',             -- 明确的表名引用
    user_id BIGINT NOT NULL COMMENT '用户ID',
    message_count INT DEFAULT 0 COMMENT '消息数量',      -- 清晰的语义
    is_active BOOLEAN DEFAULT TRUE COMMENT '是否活跃',   -- 布尔值用is_前缀
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',

    INDEX idx_tenant_bot (tenant_id, bot_id),
    INDEX idx_user_active (user_id, is_active)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='Bot对话表';

-- ❌ 错误的命名
CREATE TABLE botConversations (
    ID BIGINT PRIMARY KEY,              -- 应使用小写id
    TenantID VARCHAR(64),               -- 应使用下划线
    BotID BIGINT,
    msgCount INT,                       -- 应使用完整单词message_count
    active BOOLEAN,                     -- 应使用is_active前缀
    createTime DATETIME                 -- 应使用下划线created_at
);
```

**命名规范清单**:
- ✅ 表名: 小写 + 下划线 + 复数形式 (users, bot_conversations)
- ✅ 字段名: 小写 + 下划线 (user_id, created_at)
- ✅ 布尔字段: is_ 前缀 (is_active, is_deleted)
- ✅ 时间字段: _at 后缀 (created_at, updated_at, deleted_at)
- ✅ 外键字段: _id 后缀 (user_id, bot_id)
- ✅ 枚举字段: 清晰的描述 (status, type, category)
- ❌ 避免驼峰命名 (userID, createTime)
- ❌ 避免缩写 (msg → message, usr → user)
- ❌ 避免数字后缀 (name1, name2)

#### 1.2.2 数据类型选择

**整型选择**:
```sql
-- ✅ 正确的整型选择
id BIGINT UNSIGNED,              -- 主键使用BIGINT UNSIGNED
user_id BIGINT,                  -- 外键使用BIGINT
status TINYINT UNSIGNED,         -- 状态使用TINYINT (0-255)
count INT UNSIGNED,              -- 计数使用INT
is_enabled BOOLEAN,              -- 布尔值使用BOOLEAN

-- 数据类型范围对照表
-- TINYINT:   1字节, -128~127 或 0~255 (状态、标志位)
-- SMALLINT:  2字节, -32768~32767 或 0~65535 (小范围计数)
-- INT:       4字节, -2.1B~2.1B 或 0~4.2B (普通计数)
-- BIGINT:    8字节, -9.2E18~9.2E18 (主键、大数计数)
```

**字符串选择**:
```sql
-- ✅ 正确的字符串选择
name VARCHAR(255),                -- 变长字符串,最大255
description TEXT,                 -- 长文本使用TEXT
config JSON,                      -- JSON配置使用JSON类型
email VARCHAR(255),               -- 邮箱使用VARCHAR
phone VARCHAR(20),                -- 电话使用VARCHAR(含区号+分机)
url VARCHAR(512),                 -- URL使用VARCHAR(可长)

-- VARCHAR vs TEXT 选择规则
-- 0-255字符:   VARCHAR(255)
-- 256-65535字符: VARCHAR(实际长度) 或 TEXT
-- >65535字符:  LONGTEXT
-- JSON数据:   使用JSON类型(MySQL 5.7+)
```

**时间类型选择**:
```sql
-- ✅ 正确的时间类型选择
created_at DATETIME,              -- 精确到秒
logged_at TIMESTAMP,              -- 时区相关使用TIMESTAMP
birth_date DATE,                  -- 仅日期使用DATE
scheduled_time TIME,              -- 仅时间使用TIME

-- DATETIME vs TIMESTAMP 选择
-- DATETIME:  不受时区影响,8字节存储,范围1000-9999年
-- TIMESTAMP: 自动时区转换,4字节存储,范围1970-2038年
-- 推荐: 业务时间用DATETIME,日志时间用TIMESTAMP
```

**小数类型选择**:
```sql
-- ✅ 正确的小数类型选择
price DECIMAL(10,2),              -- 金额使用DECIMAL(精度优先)
rate DECIMAL(5,4),                -- 汇率/比率使用DECIMAL
latitude DECIMAL(10,7),           -- 经纬度使用DECIMAL
rating_avg DECIMAL(3,2),          -- 评分使用DECIMAL

-- DECIMAL vs FLOAT vs DOUBLE
-- DECIMAL(p,s): 精确小数,适合金额、汇率
-- FLOAT:      近似值,4字节,范围较大
-- DOUBLE:     近似值,8字节,范围最大
-- 推荐: 财务数据必须用DECIMAL
```

#### 1.2.3 约束设计

```sql
-- ✅ 完整的约束设计示例
CREATE TABLE bot_workflows (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    tenant_id VARCHAR(64) NOT NULL,
    bot_id BIGINT NOT NULL,
    name VARCHAR(255) NOT NULL,

    -- 非空约束
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,

    -- 默认值约束
    version INT DEFAULT 1,
    is_published BOOLEAN DEFAULT FALSE,
    status ENUM('draft', 'published', 'archived') DEFAULT 'draft',

    -- 唯一约束
    UNIQUE KEY uk_tenant_bot_name (tenant_id, bot_id, name),

    -- 检查约束 (MySQL 8.0.16+)
    CONSTRAINT chk_version CHECK (version >= 1),

    -- 外键约束
    FOREIGN KEY (bot_id) REFERENCES bots(id) ON DELETE CASCADE,

    -- 索引
    INDEX idx_tenant_id (tenant_id),
    INDEX idx_bot_id (bot_id),
    INDEX idx_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 约束设计原则
-- 1. 主键: 使用BIGINT AUTO_INCREMENT
-- 2. 非空: 重要业务字段必须NOT NULL
-- 3. 默认值: 为字段提供合理的默认值
-- 4. 唯一: 业务唯一性约束(如用户名、邮箱)
-- 5. 外键: 保持引用完整性,考虑级联策略
-- 6. 检查: 数据有效性验证(MySQL 8.0+支持)
```

### 1.3 表关系设计

#### 1.3.1 一对一关系

```sql
-- 场景: Bot与Bot配置是一对一
CREATE TABLE bots (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    tenant_id VARCHAR(64) NOT NULL,
    name VARCHAR(255) NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE bot_configs (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    bot_id BIGINT NOT NULL UNIQUE,       -- UNIQUE确保一对一
    prompt TEXT,
    settings JSON,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,

    FOREIGN KEY (bot_id) REFERENCES bots(id) ON DELETE CASCADE,
    INDEX idx_bot_id (bot_id)
);

-- 查询示例
SELECT b.*, c.prompt, c.settings
FROM bots b
LEFT JOIN bot_configs c ON b.id = c.bot_id
WHERE b.id = 123;
```

#### 1.3.2 一对多关系

```sql
-- 场景: Bot与对话记录是一对多
CREATE TABLE bot_conversations (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    tenant_id VARCHAR(64) NOT NULL,
    bot_id BIGINT NOT NULL,               -- 外键,不需要UNIQUE
    user_id BIGINT NOT NULL,
    title VARCHAR(255),
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,

    FOREIGN KEY (bot_id) REFERENCES bots(id) ON DELETE CASCADE,
    INDEX idx_bot_id (bot_id),           -- 提升关联查询性能
    INDEX idx_user_id (user_id),
    INDEX idx_tenant_bot (tenant_id, bot_id)
);

-- 查询示例: 获取Bot的所有对话
SELECT b.name AS bot_name, c.*
FROM bot_conversations c
INNER JOIN bots b ON c.bot_id = b.id
WHERE b.id = 123
ORDER BY c.created_at DESC
LIMIT 20;
```

#### 1.3.3 多对多关系

```sql
-- 场景: Bot与插件是多对多
CREATE TABLE bots (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(255) NOT NULL
);

CREATE TABLE plugins (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(255) NOT NULL
);

-- 中间表 (关联表)
CREATE TABLE bot_plugins (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    bot_id BIGINT NOT NULL,
    plugin_id BIGINT NOT NULL,
    config JSON,                          -- 关联时的配置
    enabled BOOLEAN DEFAULT TRUE,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,

    -- 复合唯一索引
    UNIQUE KEY uk_bot_plugin (bot_id, plugin_id),

    -- 外键约束
    FOREIGN KEY (bot_id) REFERENCES bots(id) ON DELETE CASCADE,
    FOREIGN KEY (plugin_id) REFERENCES plugins(id) ON DELETE CASCADE,

    -- 单列索引(优化查询)
    INDEX idx_bot_id (bot_id),
    INDEX idx_plugin_id (plugin_id)
);

-- 查询示例: 获取Bot的所有插件
SELECT p.*, bp.config, bp.enabled
FROM bot_plugins bp
INNER JOIN plugins p ON bp.plugin_id = p.id
WHERE bp.bot_id = 123 AND bp.enabled = TRUE;
```

## 2. 索引优化最佳实践

### 2.1 索引设计原则

#### 2.1.1 选择合适的索引列

```sql
-- ✅ 适合建索引的列
-- 1. WHERE条件列
INDEX idx_user_id (user_id)
-- 2. ORDER BY排序列
INDEX idx_created_at (created_at DESC)
-- 3. JOIN关联列
INDEX idx_bot_id (bot_id)
-- 4. 覆盖索引(包含查询所需的所有列)
INDEX idx_user_status_created (user_id, status, created_at, id)

-- ❌ 不适合建索引的列
-- 1. 低选择性列(如性别、状态)
-- INDEX idx_gender (gender)  -- gender只有男/女/未知,选择性低
-- 2. 频繁更新的列(避免索引维护开销)
-- INDEX idx_last_active (last_active)  -- 每次访问都更新
-- 3. TEXT/BLOB大字段(不建议直接建索引)
-- INDEX idx_description (description)  -- 使用全文索引替代
```

#### 2.1.2 索引选择性评估

```sql
-- 选择性 = DISTINCT值数量 / 总行数
-- 选择性越高,索引效果越好 (接近1为最优)

-- 示例: 评估user_id字段的选择性
SELECT
    COUNT(*) AS total_rows,
    COUNT(DISTINCT user_id) AS distinct_values,
    COUNT(DISTINCT user_id) / COUNT(*) AS selectivity
FROM bot_conversations;

-- 选择性判断标准
-- > 0.9:  优秀,强烈建议建索引
-- 0.7-0.9: 良好,建议建索引
-- 0.5-0.7: 一般,考虑建索引
-- 0.1-0.5: 较差,谨慎建索引
-- < 0.1:   很差,不建议建索引(如gender, is_active)
```

#### 2.1.3 复合索引设计

```sql
-- ✅ 正确的复合索引设计
-- 1. 最左前缀原则
INDEX idx_a_b_c (user_id, status, created_at)

-- 以下查询可以使用索引:
SELECT * FROM bot_conversations WHERE user_id = 123;                    -- ✅ 使用user_id
SELECT * FROM bot_conversations WHERE user_id = 123 AND status = 1;     -- ✅ 使用user_id+status
SELECT * FROM bot_conversations WHERE user_id = 123 AND status = 1 AND created_at > '2025-01-01';  -- ✅ 使用完整索引

-- 以下查询无法使用索引:
SELECT * FROM bot_conversations WHERE status = 1;                       -- ❌ 跳过了user_id
SELECT * FROM bot_conversations WHERE created_at > '2025-01-01';         -- ❌ 跳过了user_id和status
SELECT * FROM bot_conversations WHERE status = 1 AND created_at > '2025-01-01' AND user_id = 123;  -- ✅ 使用了完整索引(优化器会重排)

-- 2. 复合索引列顺序原则
-- 等值查询列放在前面,范围查询列放在后面
INDEX idx_user_status_created (user_id, status, created_at)

-- 3. 覆盖索引设计(包含SELECT所需的所有列)
INDEX idx_user_status_created_id_title (user_id, status, created_at, id, title)
-- 查询时无需回表,直接从索引获取数据
SELECT id, title FROM bot_conversations
WHERE user_id = 123 AND status = 1
ORDER BY created_at DESC LIMIT 20;
```

### 2.2 索引优化清单

#### 2.2.1 主键索引

```sql
-- ✅ 标准: 每个表必须有主键
CREATE TABLE users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,  -- 推荐使用自增BIGINT
    name VARCHAR(255)
);

-- ✅ 自增主键优势
-- 1. 插入性能好(顺序插入,减少页分裂)
-- 2. 占用空间小(BIGINT 8字节)
-- 3. 支持大表(千亿级数据)
```

#### 2.2.2 唯一索引

```sql
-- ✅ 业务唯一性约束
CREATE TABLE users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    email VARCHAR(255) NOT NULL UNIQUE,      -- 邮箱唯一
    username VARCHAR(100) NOT NULL UNIQUE,   -- 用户名唯一
    phone VARCHAR(20) UNIQUE,                -- 手机号唯一(可空)

    UNIQUE KEY uk_email (email),
    UNIQUE KEY uk_username (username),
    UNIQUE KEY uk_phone (phone)
);

-- 联合唯一索引
CREATE TABLE bot_followers (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    bot_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,

    UNIQUE KEY uk_bot_user (bot_id, user_id)  -- 一个用户只能关注一次Bot
);
```

#### 2.2.3 普通索引

```sql
-- ✅ 单列索引
CREATE TABLE bot_conversations (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    bot_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    status TINYINT NOT NULL,
    created_at DATETIME NOT NULL,

    INDEX idx_bot_id (bot_id),          -- 按Bot查询
    INDEX idx_user_id (user_id),         -- 按用户查询
    INDEX idx_status (status),            -- 按状态查询
    INDEX idx_created_at (created_at)     -- 按时间查询
);
```

#### 2.2.4 复合索引

```sql
-- ✅ 常见查询模式的复合索引
CREATE TABLE bot_conversations (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    tenant_id VARCHAR(64) NOT NULL,
    bot_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    status TINYINT NOT NULL,
    created_at DATETIME NOT NULL,

    -- 场景1: 按租户+Bot+状态查询
    INDEX idx_tenant_bot_status (tenant_id, bot_id, status),

    -- 场景2: 按用户+状态+时间排序
    INDEX idx_user_status_created (user_id, status, created_at DESC),

    -- 场景3: 按租户查询(包含统计信息)
    INDEX idx_tenant_created (tenant_id, created_at DESC)
);
```

### 2.3 索引优化建议

#### 2.3.1 索引覆盖查询

```sql
-- ✅ 创建覆盖索引,避免回表
-- 假设经常执行以下查询:
SELECT id, title, created_at
FROM bot_conversations
WHERE user_id = 123 AND status = 1
ORDER BY created_at DESC LIMIT 20;

-- 创建覆盖索引(包含查询所需的所有列)
CREATE INDEX idx_user_status_created_id_title
ON bot_conversations(user_id, status, created_at DESC, id, title);

-- 执行计划: Using index (无需回表)
EXPLAIN SELECT id, title, created_at
FROM bot_conversations
WHERE user_id = 123 AND status = 1
ORDER BY created_at DESC LIMIT 20;
```

#### 2.3.2 避免索引失效

```sql
-- ❌ 导致索引失效的常见错误

-- 1. 在索引列上使用函数
-- WHERE DATE(created_at) = '2025-01-01'        -- ❌ 失效
-- WHERE created_at >= '2025-01-01' AND created_at < '2025-01-02'  -- ✅ 正确

-- 2. 隐式类型转换
-- WHERE phone_number = 13800138000  -- ❌ phone_number是VARCHAR,数字导致隐式转换
-- WHERE phone_number = '13800138000' -- ✅ 正确

-- 3. 前缀模糊查询
-- WHERE name LIKE '%张%'              -- ❌ 失效(全模糊)
-- WHERE name LIKE '张%'               -- ✅ 有效(前缀匹配)
-- WHERE name LIKE '%张'               -- ❌ 失效(后缀匹配)

-- 4. OR连接(如果没有索引)
-- WHERE user_id = 123 OR status = 1   -- ❌ 如果status无索引,导致全表扫描
-- WHERE user_id = 123 UNION WHERE status = 1  -- ✅ 改用UNION

-- 5. 负向查询
-- WHERE status != 1                   -- ❌ 不等于通常不走索引
-- WHERE status IN (1, 2, 3)           -- ✅ 改用IN

-- 6. IS NULL查询
-- WHERE deleted_at IS NULL            -- ✅ 可以使用索引
-- WHERE deleted_at IS NOT NULL        -- ✅ 可以使用索引
```

## 5. 性能优化建议

### 5.1 SQL优化

#### 5.1.1 慢查询优化

```sql
-- ❌ 慢查询示例(全表扫描)
SELECT * FROM bot_conversations
WHERE DATE(created_at) = '2025-01-30';

-- ✅ 优化后(使用索引)
SELECT * FROM bot_conversations
WHERE created_at >= '2025-01-30'
  AND created_at < '2025-01-31';

-- 分析执行计划
EXPLAIN SELECT * FROM bot_conversations
WHERE created_at >= '2025-01-30'
  AND created_at < '2025-01-31';
```

#### 5.1.2 SELECT优化

```sql
-- ❌ 避免 SELECT *
SELECT * FROM bots;  -- 查询所有列,增加网络传输和IO

-- ✅ 只查询需要的列
SELECT id, name, status FROM bots;

-- ❌ 避免子查询
SELECT * FROM bots
WHERE id IN (SELECT bot_id FROM bot_conversations WHERE user_id = 123);

-- ✅ 改用JOIN
SELECT DISTINCT b.*
FROM bots b
INNER JOIN bot_conversations c ON b.id = c.bot_id
WHERE c.user_id = 123;

-- ❌ 避免OR
SELECT * FROM bots
WHERE tenant_id = 'tenant_123' OR status = 'published';

-- ✅ 改用UNION
SELECT * FROM bots WHERE tenant_id = 'tenant_123'
UNION
SELECT * FROM bots WHERE status = 'published';

-- ✅ 或者改用复合索引
CREATE INDEX idx_tenant_status ON bots(tenant_id, status);
SELECT * FROM bots
WHERE tenant_id = 'tenant_123' OR status = 'published';
-- 如果idx_tenant_status是覆盖索引,可能也会走索引
```

#### 5.1.3 JOIN优化

```sql
-- ❌ 交叉连接(笛卡尔积)
SELECT * FROM bots, plugins;  -- 产生M*N行结果

-- ✅ 使用INNER JOIN并添加条件
SELECT * FROM bots
INNER JOIN bot_plugins ON bots.id = bot_plugins.bot_id;

-- ✅ 小表驱动大表原则
-- 将小表放在JOIN前面
SELECT *
FROM (SELECT * FROM users WHERE id = 123) u  -- 小表
INNER JOIN bot_conversations c ON c.user_id = u.id;  -- 大表

-- ✅ 只查询需要的列,避免回表
SELECT c.id, c.title, b.name AS bot_name
FROM bot_conversations c
INNER JOIN bots b ON c.bot_id = b.id
WHERE c.user_id = 123;
```

#### 5.1.4 分页优化

```sql
-- ❌ 深分页性能差
SELECT * FROM bot_conversations
ORDER BY id
LIMIT 1000000, 20;  -- 跳过100万行,查询慢

-- ✅ 使用延迟关联优化
SELECT * FROM bot_conversations
WHERE id > (
  SELECT id FROM bot_conversations
  ORDER BY id
  LIMIT 1000000, 1
)
ORDER BY id
LIMIT 20;

-- ✅ 使用游标分页(推荐)
-- 首次查询
SELECT * FROM bot_conversations
ORDER BY id
LIMIT 20;

-- 后续查询(记住上一页最后的id)
SELECT * FROM bot_conversations
WHERE id > 上一页最后的id
ORDER BY id
LIMIT 20;
```

#### 5.4.2 缓存层

```python
# Redis缓存策略
import redis
import hashlib
import json

class CacheService:
    def __init__(self):
        self.redis = redis.Redis(host='localhost', port=6379, db=0)

    def get_bot(self, bot_id):
        # 缓存键
        cache_key = f"bot:{bot_id}"

        # 尝试从缓存获取
        cached = self.redis.get(cache_key)
        if cached:
            return json.loads(cached)

        # 缓存未命中,从数据库查询
        bot = db.query("SELECT * FROM bots WHERE id = ?", bot_id)
        if bot:
            # 写入缓存(TTL=1小时)
            self.redis.setex(cache_key, 3600, json.dumps(bot))

        return bot

    def invalidate_bot(self, bot_id):
        # 缓存失效
        cache_key = f"bot:{bot_id}"
        self.redis.delete(cache_key)
```
