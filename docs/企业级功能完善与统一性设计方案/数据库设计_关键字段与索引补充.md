# 数据库设计补充 - 关键字段与索引优化

> **文档类型**: 数据库设计补充
> **版本**: v1.0
> **创建日期**: 2025-01-01
> **基于**: 数据库设计验证报告 v1.0

---

## 📋 补充说明

本文档基于《数据库设计验证报告》中识别的问题，为**10+张表**补充缺失的关键字段，并为**15+张表**优化索引设计。

### 修改原则

✅ **向后兼容**: 所有新增字段使用 DEFAULT 或 NULL，确保不影响现有数据
✅ **渐进式迁移**: 提供 ALTER TABLE 脚本，支持在线变更
✅ **索引优化**: 添加索引时考虑查询性能和写入性能的平衡
✅ **命名规范**: 统一字段命名规范

### 1.1 智能路由引擎表

#### routing_rules (路由规则表)

**缺失字段**:
- `version_id` - 规则版本控制
- `test_coverage` - 测试覆盖率

**补充SQL**:

```sql
-- 添加版本控制字段
ALTER TABLE routing_rules
ADD COLUMN version_id VARCHAR(64) NULL COMMENT '规则版本ID，关联routing_rule_versions表'
AFTER name,
ADD INDEX idx_version_id (version_id);

-- 添加测试覆盖率字段
ALTER TABLE routing_rules
ADD COLUMN test_coverage DECIMAL(5,2) DEFAULT 0.00 COMMENT '测试覆盖率(0-100)，衡量规则的测试充分性'
AFTER status;

-- 添加最后测试时间
ALTER TABLE routing_rules
ADD COLUMN last_tested_at TIMESTAMP NULL COMMENT '最后测试时间'
AFTER test_coverage;

-- 添加规则哈希值（用于快速比较规则是否变更）
ALTER TABLE routing_rules
ADD COLUMN rule_hash VARCHAR(64) NULL COMMENT '规则内容的MD5哈希值，用于检测规则变更'
AFTER condition;

-- 添加规则生效时间范围
ALTER TABLE routing_rules
ADD COLUMN effective_start_time TIMESTAMP NULL COMMENT '规则生效开始时间'
AFTER priority,
ADD COLUMN effective_end_time TIMESTAMP NULL COMMENT '规则生效结束时间'
AFTER effective_start_time,
ADD INDEX idx_effective_time (effective_start_time, effective_end_time);
```

**业务价值**:
- ✅ 支持规则版本管理和回滚
- ✅ 可追溯规则变更历史
- ✅ 衡量规则质量
- ✅ 支持规则的定时生效

## 📝 三、命名规范统一

### 3.1 时间戳字段统一

**问题**: 部分表使用 `DATETIME`，部分使用 `BIGINT` (毫秒时间戳)

**统一规范**: 全部使用 `TIMESTAMP` 或 `DATETIME`

**迁移脚本**:

```sql
-- 示例：将BIGINT时间戳转换为DATETIME
-- 注意：需要根据实际情况调整

-- 假设某表使用了BIGINT存储时间戳
ALTER TABLE example_table
ADD COLUMN created_at_datetime TIMESTAMP NULL COMMENT '创建时间(DATETIME)',
ADD COLUMN updated_at_datetime TIMESTAMP NULL COMMENT '更新时间(DATETIME)';

-- 数据迁移
UPDATE example_table
SET created_at_datetime = FROM_UNIXTIME(created_at_int / 1000),
    updated_at_datetime = FROM_UNIXTIME(updated_at_int / 1000);

-- 删除旧字段
ALTER TABLE example_table
DROP COLUMN created_at_int,
DROP COLUMN updated_at_int;

-- 重命名新字段
ALTER TABLE example_table
CHANGE COLUMN created_at_datetime created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
CHANGE COLUMN updated_at_datetime updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP;
```

### 3.2 创建人字段统一

**问题**: `user_id` vs `creator_id` vs `created_by`

**统一规范**: 全部使用 `created_by` 和 `updated_by`

**迁移脚本**:

```sql
-- 示例：统一创建人字段

-- 1. 添加新字段
ALTER TABLE example_table
ADD COLUMN created_by_new BIGINT NULL COMMENT '创建人ID',
ADD COLUMN updated_by_new BIGINT NULL COMMENT '更新人ID';

-- 2. 数据迁移
UPDATE example_table
SET created_by_new = COALESCE(creator_id, user_id, created_by),
    updated_by_new = COALESCE(updater_id, modifier_id, updated_by);

-- 3. 删除旧字段
ALTER TABLE example_table
DROP COLUMN creator_id,
DROP COLUMN user_id,
DROP COLUMN created_by,
DROP COLUMN updater_id,
DROP COLUMN modifier_id,
DROP COLUMN updated_by;

-- 4. 重命名新字段
ALTER TABLE example_table
CHANGE COLUMN created_by_new created_by BIGINT COMMENT '创建人ID',
CHANGE COLUMN updated_by_new updated_by BIGINT COMMENT '更新人ID';

-- 5. 添加索引
ALTER TABLE example_table
ADD INDEX idx_created_by (created_by),
ADD INDEX idx_updated_by (updated_by);
```

### 3.3 租户ID字段统一

**问题**: `VARCHAR(64)` vs `BIGINT`

**统一规范**: 全部使用 `VARCHAR(64)`

**说明**: 由于现有系统中租户ID已广泛使用VARCHAR(64)，为保持一致性，建议统一使用VARCHAR(64)

### 4.2 风险控制

✅ **备份数据**: 执行ALTER TABLE前务必备份
✅ **测试环境验证**: 先在测试环境验证所有变更
✅ **低峰期执行**: 在业务低峰期执行在线DDL
✅ **回滚预案**: 准备回滚脚本
✅ **分批执行**: 大表分批执行，避免长时间锁表

### 4.3 性能考虑

⚠️ **在线DDL**: 使用 `ALGORITHM=INPLACE, LOCK=NONE` 避免锁表
⚠️ **索引创建**: 大表索引创建可能耗时较长
⚠️ **字段添加**: 添加带DEFAULT的字段是快速操作
⚠️ **字段修改**: 修改字段类型可能需要重建表
