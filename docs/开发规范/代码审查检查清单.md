## 二、代码质量 (Code Quality)

### 2.1 命名规范

- [ ] **变量命名**: 使用`camelCase`，见名知意
- [ ] **常量命名**: 使用`UPPER_SNAKE_CASE`
- [ ] **函数命名**: 动词开头，如`getUserById()`
- [ ] **类型命名**: 使用`PascalCase`
- [ ] **包命名**: 小写单词，不使用下划线

**❌ 错误示例**:
```go
// ❌ 变量命名不规范
var data1 interface{}
var user_info User

// ✅ 正确命名
var userData interface{}
var userInfo User
```

### 2.2 代码结构

- [ ] **函数职责单一**: 每个函数只做一件事
- [ ] **函数长度**: 不超过50行
- [ ] **文件长度**: 不超过500行
- [ ] **嵌套层次**: 不超过3层
- [ ] **圈复杂度**: 不超过10

### 2.3 DRY原则

- [ ] **无重复代码**: 相同逻辑只实现一次
- [ ] **抽象公共逻辑**: 提取为函数/方法
- [ ] **复用现有组件**: 不重复造轮子

### 2.4 SOLID原则

- [ ] **单一职责(SRP)**: 类/模块职责单一
- [ ] **开闭原则(OCP)**: 对扩展开放，对修改关闭
- [ ] **里氏替换(LSP)**: 子类可替换父类
- [ ] **接口隔离(ISP)**: 接口专一，不臃肿
- [ ] **依赖倒置(DIP)**: 依赖抽象而非实现

## 四、性能 (Performance)

### 4.1 数据库

- [ ] **索引**: 查询字段有索引支持
- [ ] **N+1问题**: 避免N+1查询
- [ ] **分页**: 大数据量查询使用分页
- [ ] **批量操作**: 批量插入/更新使用事务

**❌ 错误示例**:
```go
// ❌ N+1查询
users, _ := db.Find(&users)
for _, user := range users {
    db.Where("user_id = ?", user.ID).Find(&orders)  // N+1
}

// ✅ 使用Preload
users, _ := db.Preload("Orders").Find(&users)
```

### 4.2 缓存

- [ ] **热点数据**: 热点数据使用Redis缓存
- [ ] **缓存失效**: 有合理的缓存失效策略
- [ ] **缓存穿透**: 不存在的数据也缓存空值
- [ ] **缓存雪崩**: 设置随机过期时间

### 4.3 并发

- [ ] **并发安全**: 共享资源使用锁保护
- [ ] **goroutine泄漏**: 确保goroutine能正确退出
- [ ] **context使用**: 使用context控制超时

## 七、Go语言特定 (Go Specific)

### 7.1 错误处理

- [ ] **错误检查**: 所有错误都检查

- [ ] **错误码**: 使用业务错误码

### 7.2 并发

- [ ] **goroutine**: goroutine有明确的退出路径
- [ ] **channel**: channel使用正确，避免死锁
- [ ] **sync包**: Mutex/RWMutex使用正确
- [ ] **context**: 使用context传递超时和取消

**❌ 错误示例**:
```go
// ❌ goroutine泄漏
go func() {
    for {
        doSomething()  // 无法退出
    }
}()

// ✅ 使用context
go func() {
    for {
        select {
        case <-ctx.Done():
            return
        default:
            doSomething()
        }
    }
}()
```

## 审查流程

### 1. 提交前自检

```bash
# 运行代码检查
rush lint

# 运行测试
rush test

# 格式化代码
gofmt -w .
npm run format
```

### 2. 创建Pull Request

- [ ] PR标题使用规范格式：`feat(bot): 添加Bot创建功能`
- [ ] PR描述包含：修改说明、修改截图、相关Issue
- [ ] 标记Reviewers（至少1人）

### 3. 代码审查

- [ ] 使用本清单逐项检查
- [ ] 标记问题为`Must Fix`或`Suggestion`
- [ ] 重大问题必须修复才能合并

### 4. 修改与合并

- [ ] 开发者修复问题
- [ ] Reviewer再次审查
- [ ] 确认无问题后批准合并
- [ ] 使用Squash and Merge合并
